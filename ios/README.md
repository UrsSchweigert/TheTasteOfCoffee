# Cupmark iOS app

SwiftUI app, iOS 17 or later, no third-party packages. Builds only on macOS with Xcode 16 or later.

## Vocabulary

- The app bundles `contracts/vocabulary/v<N>/` and `contracts/i18n/` through two Xcode folder references (bundle paths `v<N>/` and `i18n/`). Nothing is copied into `ios/`.
- `Generated/Vocabulary.swift` holds one enum per list (raw value = contract id), the ranges, the constants and the label languages. Regenerate it after a vocabulary change:

  ```
  (cd contracts && npm ci)
  node scripts/generate-ios-vocabulary.mjs
  ```

  `node scripts/generate-ios-vocabulary.mjs --check` fails if the file is out of date or if the project bundles a different version. CI runs it on Linux.
- When a new vocabulary version is published, the check fails until the folder reference in `project.pbxproj` points at the new `v<N>` directory and the Swift file is regenerated.
- Raw values are always the contract ids. Case names are the ids in lowerCamelCase, with one exception: an id that would read as `Optional.none` or `Optional.some` is named after its list, so `none` in `milk_types` is `Vocabulary.MilkType.noMilk` (raw value `"none"`). `.none` on an optional vocabulary value therefore always means nil.
- A region in `origins` names its country (ADR 0011). The generator emits that as a typed property, `Vocabulary.Origin.country: Vocabulary.Origin?` (`.sumatra.country == .indonesia`, nil for a country), not as a string. Lists with the same id in different namespaces, such as `java` in `origins` and `varieties`, are separate enums (`Vocabulary.Origin.java`, `Vocabulary.Variety.java`).
- From vocabulary v3 on (M2-T3, ADR 0021), two more shapes are generated, and only when the bundled version has them, so the v2 output is unchanged. A grinder's own dial (`ENTRY_RANGES` in `contracts/lib/vocabulary.mjs`) becomes `Vocabulary.Grinder.scale: VocabularyRange?`, nil for a grinder without a scale. The method field rules (`brew.json`, `field_rules`) become a typed table: `Vocabulary.BrewField` (every BrewParameters field of `contracts/openapi.yaml` but `method`, raw value = API property; `scaledBy` names the field whose picked entry's scale a value lies on, `grind_setting` on `grinder`), `Vocabulary.Method.fieldRules`, `allows(_:)` and `allowedFields`. A field without a rule is allowed with every method. The rules are never constants, and generation fails on a rule that names an unknown method or field, or a scale off its step. The app reads scales and rules through these types only; `VocabularyStore.entryRanges` keeps the bundled entry ranges by `<namespace>.<id>.<attribute>` for checks, never in `ranges` and never by index.
- `VocabularyStore.load(from:)` decodes the bundled JSON at runtime and resolves labels with `label(namespace:id:language:)`. Errors are thrown, never trapped.

## API types

`Generated/API.swift` holds the request and response types of `contracts/openapi.yaml`, written by `scripts/generate-ios-api.mjs` (ADR 0022). It needs no Swift package and runs on Linux. Regenerate it after a contract change:

```
(cd contracts && npm ci)
node scripts/generate-ios-api.mjs
```

`node scripts/generate-ios-api.mjs --check` fails if the file is out of date; CI runs it in the `contracts` job. `--file=<path>` checks or writes another file; the script tests use it.

- Every operation the app calls is covered: beans, barcodes, Open Food Facts, catalogue images, label photos, shelf, brews, recipes, profile, export and account. `API.Endpoint` lists them with method, path, success status, request and response schema, and media type (`image/jpeg` for catalogue images, `text/csv` for the export), and the error statuses the contract lists (`documentedErrorStatuses`). Only `GET /health` is left out (`EXCLUDED_OPERATIONS`), because only the deploy smoke test calls it.
- Each object schema is a `Codable`, `Hashable`, `Sendable` struct in `enum API` (`API.Brew`, `API.BrewInput`, ...), conforming to `APIObject`. It has explicit snake_case `CodingKeys` and nothing else, and it never encodes null. `API.Schemas` lists every schema's properties, which the tests use to check encoded JSON.
- Vocabulary values use the generated `Vocabulary.*` enums and `VocabularyLanguage`, so no list exists twice. The generator fails if an `x-vocabulary` enum and the bundled vocabulary disagree.
- `dose_dg` is an integer (`API.DoseDg`, ADR 0004). `doseGrams` reads and sets it in grams, rounding to 0.1 g, and never traps.
- `API.CalendarDate` is a day (`YYYY-MM-DD`) without a time zone. `API.Timestamp` is RFC 3339, sent in UTC with milliseconds (`2026-11-25T08:30:00.123Z`), and held as whole milliseconds, so it survives a JSON round trip exactly.
- `water_temp_c` and `water_temp_special` are one optional `API.WaterTemperature` (`.celsius(94)` or `.special(...)`), so both can never be set. A response with both fails to decode.
- In a page (`ShelfEntryPage`, `BrewPage`, `RecipePage`), each item decodes on its own. An item that fails, for example because it holds an id the bundled vocabulary does not know, is left out of `items` and listed in `undecodableItems`. A single resource that fails throws a `DecodingError`. Nothing traps.

## API client

`Networking/APIClient.swift` (M2-T8) calls the API with `URLSession` and async/await, one method per operation of `API.Endpoint`. It needs no package.

- The base URL is injected (M2-T9). The default session is ephemeral, with no URL cache and no cookies.
- Method, path, success status and `Accept` come from `API.Endpoint`. Path parameters are `ResourceID` (a ULID, checked against the contract's `Id` pattern) or `LookupBarcode` (12 or 13 digits) only, so no path is built from other text. `cursor` and `limit` are checked too.
- Every request carries `Authorization: Bearer <token>` from a `TokenProvider` (`currentAccessToken()`, `refresh()`; `AuthSession` implements it, see Sign-in). No path, query or body names a user (invariant 3). On a 401 the client calls `refresh()` once and sends the request once more; a second 401, a failed refresh or no token is `APIError.unauthorized`. A refresh that fails at Cognito rather than for the user is retryable instead (`APIClient.tokenFailure`, M2-T11): transport stays `transport`, a Cognito 5xx or unusable token response is `serviceUnavailable`, a Cognito 429 is `tooManyRequests`.
- Any status other than the route's success status throws `APIError`: `badRequest`, `unauthorized`, `notFound`, `conflict`, `tooManyRequests`, `serviceUnavailable`, `server(status:)`, `unexpectedStatus` (also a 2xx other than the documented one), plus `transport(URLError.Code)`, `undecodable` and `invalidResponse`. Error bodies are not read. The client logs nothing, so no body, token or Open Food Facts text reaches a log (docs/05, Security).
- `allShelfEntries()`, `allBrews()` and `allRecipes()` follow `next_cursor` with `limit=100` until it is absent. Items that do not decode are collected in `undecodableItems`. A repeated or malformed cursor, or more than 1,000 pages (`APIClient.maxPages`), stops with `invalidResponse`.
- Cancelling the calling task throws `CancellationError`, never `transport(.cancelled)`, and nothing is refreshed or retried after it.
- `catalogueImage(_:)` loads `GET /catalogue_images/{image_id}` with the token (never `AsyncImage`), checks that the body is a JPEG and caches it in `Library/Caches/CatalogueImages/<image_id>.jpg` (`CatalogueImageCache`). An image never changes under its id, so a cached one is never fetched again. The cache is bounded at 50 MiB and drops the least recently used files first.
- Label photo bytes are not sent by this client: `LabelPhotoUploader` sends the presigned S3 POST of `createLabelPhotoUpload` through its own transport, without the token (M2-T24, see Label photo).
- Tests (`APIClientTests`) use a `URLProtocol` stub (`CupmarkTests/Support/StubURLProtocol.swift`), one fake host per server.

## Stage configuration

`Configuration/StageConfig.swift` (M2-T9) holds the endpoints of the backend stage the app was built for. They are not secrets: the Cognito app client is public and has no secret (infra/src/identity.ts).

- `Config/Dev.xcconfig` and `Config/Prod.xcconfig` set `CUPMARK_STAGE`, `CUPMARK_HOSTED_DOMAIN` (`https://cupmark-<stage>.auth.eu-central-1.amazoncognito.com`), `CUPMARK_APP_CLIENT_ID` (stack output `IdentityAppClientId...`), `CUPMARK_API_URL` (stack output `ApiUrl`), `CUPMARK_REDIRECT_URL` (`cupmark://auth`) and `CUPMARK_SIGN_OUT_URL` (`cupmark://signout`). `//` starts a comment in an xcconfig, so URLs are written `https:/$()/...`; `$()` expands to nothing.
- `Config/Info.plist` maps them to the keys `CupmarkStage`, `CupmarkHostedDomain`, `CupmarkAppClientID`, `CupmarkAPIURL`, `CupmarkRedirectURL` and `CupmarkSignOutURL`. Xcode merges it with the generated Info.plist (`GENERATE_INFOPLIST_FILE` stays on, `INFOPLIST_FILE = Config/Info.plist`). It sits outside the synchronized `Cupmark/` folder, so it is not also copied as a resource.
- Debug and Release of the app target both use `Dev.xcconfig` until prod is deployed in M6 (ADR 0023). `Prod.xcconfig` is not referenced yet.
- `StageConfig(info:)` checks every key and throws `StageConfigError.missing`, `.malformed` or `.wrongRegion` with the key, never the value. The hosted domain must be exactly `cupmark-<stage>` in eu-central-1; the API URL must be `https://<10-character api id>.execute-api.eu-central-1.amazonaws.com` with no path; the app client id letters and digits; the two callback URLs exactly the registered ones. Any region but eu-central-1 is `wrongRegion` (invariant 6). Nothing traps.
- `StageConfigLoadState.load(from: .main)` runs at launch. `.notConfigured` shows `NotConfiguredView`, and the app calls no backend. `apiBaseURL` is what `APIClient(baseURL:)` gets.
- The dev app client id and API URL are the outputs of the first dev deploy of `cupmark-dev-core` (2026-11-26, M2-T10); `testTheBuiltAppIsConfiguredWithTheDevStackValues` checks that the built app is `.configured` with them. Prod's ids are still `PLACEHOLDER-SET-IN-M6` until M6: uppercase letters and hyphens are invalid in both ids, so a prod build shows "not configured" instead of calling a wrong host.
- Tests: `StageConfigTests` (valid, missing, malformed and wrong-region values, and the keys in the built app). `scripts/ios-scripts.test.mjs` checks on Linux that both xcconfigs, `Info.plist`, `identity.ts` and the project agree.

## Barcode scanner

`Scanner/` (M2-T13) implements F1 step 1. It never offers a way to type a barcode (invariant 1).

- `CanonicalBarcode` is pure Swift and matches the backend's `canonicalBarcode` (backend/src/repository/keys.ts) exactly: 13 ASCII digits are kept, 12 get a leading 0 (UPC-A to EAN-13), and the GS1 check digit (weights 1, 3 from the left) must be right. Anything else, including whitespace and non-ASCII digits, is ignored, so no request is made for it. `lookupBarcode` gives the `LookupBarcode` path value for M2-T14.
- `BarcodeScanSession` lets the first valid code through once; every later report, duplicate or not, is ignored.
- `ScannerViewModel` checks a `ScannerEnvironment`, then reads a `BarcodeSource` (an `AsyncStream` of payloads), stops the source at the first valid code and calls `onScanned` once. Tests use `FakeBarcodeSource` and `FakeScannerEnvironment`, without VisionKit.
- `DataScannerView` wraps VisionKit's `DataScannerViewController` with `recognizedDataTypes: [.barcode(symbologies: [.ean13])]`. VisionKit has no UPC-A symbology: a UPC-A code is an EAN-13 with a leading 0 and is reported under `.ean13` as 13 digits. EAN-8 and UPC-E are not read (the contract's `Barcode` is 12 or 13 digits). `LiveScannerEnvironment` uses `DataScannerViewController.isSupported` (false on the simulator) and `isAvailable`, and asks for camera access once if it was never asked.
- When scanning is unsupported, denied or not available, `ScannerScreen` offers the pick-list entry (`onPickListEntry`, connected in M2-T22) and a Settings link (`UIApplication.openSettingsURLString`). `onScanned` is connected to the lookup in M2-T14; until then the root screen's "Scan a bag" row passes placeholders.
- The camera permission prompt is `INFOPLIST_KEY_NSCameraUsageDescription` in the app target's build settings, localised in `Cupmark/InfoPlist.xcstrings` (en, de).
- Only a device can run the camera: unit tests cover the logic, the real scan is checked in M2-T34.

## Barcode lookup

`Lookup/` (M2-T14) implements F1 steps 2 and 3 for the scanned barcode. The root's "Scan a bag" row opens `ScanFlowView`: the scanner until the first valid code, then `LookupScreen` in its place, so no tap is needed between scan and answer. The `APIClient` comes from `CupmarkApp`, built once from the stage's `apiBaseURL` and the `AuthSession` of `AuthModel`, and read through `EnvironmentValues.apiClient` (`Networking/APIClientEnvironment.swift`).

- `LookupModel` (`@MainActor`, `@Observable`) asks `GET /barcodes/{barcode}`. A 200 is the bean. A 404 asks `GET /barcodes/{barcode}/open_food_facts`; a hit waits for Confirm or Reject.
- Confirm is `POST /beans` with `barcode`, `open_food_facts_confirmed: true`, the optional picks (`attributes`; species, process and roast level are offered, the long lists come with the pick-list entry of M2-T22) and `Vocabulary.version`. No Open Food Facts text is ever sent: the server copies it from its cache (ADR 0005).
- A 409 from the Open Food Facts route or from `POST /beans` asks `GET /barcodes/{barcode}` again and shows that bean. A 409 followed by a 404 is a failure that can be retried.
- Everything else ends in `.pickList(reason)`, which offers the pick-list entry (`onPickListEntry`, a placeholder until M2-T22): `rejected`, `noProduct` (Open Food Facts 404), `limitReached` (a 429 from the Open Food Facts route, the daily lookup cap), `unavailable` (503, another 5xx, no network, or a 429 from the other routes, which is throttling rather than the cap) with "Try again", and `failed` (400, an unreadable answer) with "Try again". Reject also calls `onPickListEntry`.
- The lookup and the confirmation run in unstructured tasks started by the screen, so leaving the screen never cancels a request the server may already act on. `lookUp()` and `confirm()` ignore a second start.
- `BeanDetailView` shows the verified state, the attributes (`API.Bean.attributeRows`: one row per field, the operator's value wins over the picked one, with its source) with labels from contracts/i18n, and the Open Food Facts name, brand and image if the bean has them.
- `OpenFoodFactsSection` shows Open Food Facts name and brand with `Text(verbatim:)` only, never as a localisation key or Markdown, the image through `GET /catalogue_images/{image_id}` (`CatalogueImageView`, via `APIClient.catalogueImage` and its disk cache), and the localised ODbL attribution (`open_food_facts.attribution`) as its footer. The app never contacts Open Food Facts (ADR 0011).
- From the bean the flow continues to the shelf entry (M2-T18, see "Shelf"). The bean is cached in the local store when a shelf entry is saved for it.
- A 401 that `APIClient` could not fix with its one refresh (`APIError.unauthorized`) is `State.signInRequired` (and `BeanEntryModel.Failure.signInRequired` in the pick-list entry): `SignInAgainView` asks the user to sign in again, with a "Sign In" button that signs out so `AuthGate` shows the sign-in screen, instead of a retry that would fail the same way. The account's store and outbox stay on the device.
- Tests: `LookupModelTests` covers every answer above against `StubURLProtocol`, the POST body (exactly the four properties, no Open Food Facts text), operator-wins, the image route, and a test whose session puts `HostRecordingURLProtocol` in front of the stub: every host any path contacts is a stub API host. `scripts/ios-scripts.test.mjs` checks on Linux that no iOS file names the Open Food Facts domain and that name and brand are only shown with `Text(verbatim:)`.

## Pick-list bean entry

`BeanEntry/` (M2-T22) implements F1 step 4: with no Open Food Facts hit, or no barcode, the user describes the bean with pick lists and saves it as an unverified catalogue bean.

- `ScanFlowView` pushes `BeanEntryScreen`: from the scanner's "Describe the bean instead" without a barcode, and from the lookup's fallback (`.pickList(reason)`) or its Reject with the scanned barcode.
- `BeanEntryModel` (`@MainActor`, `@Observable`) holds the optional picks (`API.BeanAttributes`) and the optional barcode. `request` is the whole `POST /beans` body: `vocabulary_version` (`Vocabulary.version`), `attributes`, and `barcode` when one was scanned. It never sends `open_food_facts_confirmed`. `save()` sends it:
  - 201: the bean, shown with `BeanDetailView`;
  - 409: the barcode already has a bean, so `GET /barcodes/{barcode}` and that bean is used (a 409 without a barcode, or a 404 after it, can be retried);
  - 400: shown as "not accepted"; that exact body is never sent again (`rejectedRequest`), and changing a pick allows a new save;
  - anything else (no network, 429, 5xx): kept picks and "Try again".
  The save goes straight to the API, so the saved bean and its photo uploads show at once. When the answer is "anything else" and the entry has a store (`offlineStore`, the shelf's), the bean is saved on the device instead (`.savedOffline`, M2-T25, see "Offline scan and pending beans").
- Lists, all optional with "Not set", each offering the `other` and `unknown` entries its vocabulary list has:
  - origin: `IndexedPickList`, grouped by country through `Vocabulary.Origin.country` (`Vocabulary.Origin.groupedByCountry`, ADR 0011): countries sorted by label in A to Z sections, each followed by its regions, indented;
  - variety: `IndexedPickList`, sorted by label in A to Z sections;
  - species and process: short lists (`Picker` with the `navigationLink` style);
  - roast level: a segmented control with a "Clear" button, a pushed list at accessibility text sizes.
  The long lists have a tappable A to Z index on the trailing edge instead of a search field: `.searchable` is typed text (invariant 1). `PickListSections` sorts in the label language, ignoring case and diacritics, so "Äthiopien" is under A.
- There is no roaster list (ADR 0006).
- The camera stops while the entry covers the scanner: `ScannerViewModel.consume` stops its source when the run is cancelled (the screen's `.task` ends when another screen is pushed), and `ScannerScreen` stops it in `.onDisappear` too. Going back starts a new run with a new source.
- Tests: `BeanEntryModelTests` (the body with no picks and with all picks, with and without a barcode; 409, 400, retries), `PickListSectionsTests` (grouping by country, sections and sort order) and `ScannerViewModelTests` (a cancelled run stops the source).

## Label photo

`LabelPhoto/` (M2-T23, M2-T24) implements the photo of F1 step 4: the user photographs the bag's label, the app turns the capture into the JPEG the upload accepts (ADR 0016, D12) and uploads it to the saved bean.

- `LabelPhotoEncoder` is pure ImageIO and CoreGraphics (no UIKit, no state), with two entry points: an image file as `Data` (HEIC or JPEG; its orientation is read from its properties) and a `CGImage` with a `CGImagePropertyOrientation`. It:
  - draws the pixels upright into a new sRGB bitmap without alpha, over white (EXIF orientations 1 to 8; a Display P3 capture becomes sRGB, which is what a decoder assumes once the server has dropped the ICC profile);
  - scales down, never up, so the longest side is at most 4096 px (5000 × 3000 becomes 4096 × 2458; a 12-megapixel 4032 × 3024 capture keeps its size);
  - writes a baseline JPEG through ImageIO at quality 0.9, then 0.8 and so on down to the floor of 0.3, until the file is at most 8 MiB; at the floor it throws `LabelPhotoEncodingError.tooLarge`;
  - passes ImageIO only the quality, orientation 1 and JFIF "not progressive": nothing of the input's EXIF, GPS, TIFF or XMP is passed on, since only redrawn pixels reach the writer. Whatever ImageIO adds itself is cut from the file afterwards: everything but SOI, APP0 (JFIF), APP14 (Adobe) and the image segments (`removingMetadataSegments`), which is the shape `backend/src/images/jpeg.ts` accepts. The server strips again at completion (D12).
- `LabelPhotoCamera` wraps `UIImagePickerController` with the camera as its only source, photo mode and no editing. There is no photo library source. The system camera has its own shutter, Retake and Use Photo controls.
- `LabelPhotoDraft` (`@MainActor`, `@Observable`) holds the encoded photo in memory (empty, preparing, attached or failed); `BeanEntryModel.labelPhoto` is the draft of an entry. Encoding runs in a detached task. Taking another photo replaces it, and Remove drops it, also while an encoding is still running. Nothing is written to disk and nothing is sent: it is not part of `POST /beans`, and M2-T24 uploads it to the saved bean.
- `LabelPhotoSection` is the step in `BeanEntryScreen`, after the picks. It is hidden when the device has no camera (the simulator), and offers Settings when camera access is denied (`LabelPhotoCameraAvailability`, read on appear and on return to the foreground). It is optional: 3 taps (Photograph the Label, the shutter, Use Photo).
- Upload (M2-T24, ADR 0016; contracts/openapi.yaml `createLabelPhotoUpload`, `completeLabelPhoto`). The upload of the saved-bean screen needs the network; photos of a bean saved offline are queued (M2-T25, see "Offline scan and pending beans").
  - `LabelPhotoUploader` runs a `LabelPhotoUploadJob` (account, bean id, JPEG file, stage) in three steps: `POST /beans/{bean_id}/label_photos`; a `multipart/form-data` POST to `upload.url` with every presigned field under its S3 name (`key`, `bucket`, `Content-Type`, `Policy`, `X-Amz-Algorithm`, `X-Amz-Credential`, `X-Amz-Date`, `X-Amz-Security-Token` when present, `X-Amz-Signature`) and `file` last (`MultipartFormBody`, a random boundary that is checked not to occur in the file); then `POST /label_photos/{photo_id}/complete`. After its 204 the file is deleted. Before each step the job's account must still be the signed-in one (`AuthSession.isSignedIn(as:)`, as in `SyncEngine`, ADR 0025); otherwise the run stops with `signInRequired`.
  - Nothing is sent to a presigned POST that does not pass `PresignedLabelPhotoPost`: the URL must match the contract's pattern (a `cupmark-` bucket, virtual-hosted, eu-central-1), `bucket` must be that bucket, `key` must be `uploads/<photo_id>.jpg`, and every field must match its contract pattern (`LabelPhotoUploadPatterns`; `scripts/ios-scripts.test.mjs` checks they equal the contract's).
  - The S3 POST goes through `PresignedPostTransport` (live: `URLSessionPresignedPostTransport`, its own ephemeral session, no cookies, every redirect refused by `RefuseRedirectsDelegate`, so a 3xx is a failure), never through `APIClient`, so it carries no bearer token.
  - Statuses: an expiry starts a new upload once per run: `expires_at` passed or within 30 s by the device clock, or an S3 403. After that the device clock is not trusted again (the POST is sent and S3 decides) and a second 403 is `failed`, so a skewed clock or a policy S3 always refuses costs at most 2 of the 20 daily uploads. A 404 on completion starts a new upload once per run as well. 400 on completion or another S3 4xx: `rejected`, a retake is offered. 409 (or 404 or 400 when starting): `noMorePhotos`. 429: `dailyLimitReached`, "try again tomorrow". 401: sign in again. Anything else: `failed`, and the job is kept where it stopped, so "Try Again" does not repeat a successful S3 POST. A 409 after a completion that failed in transport counts as completed ("already completed" is the likely reading); if that first call never reached the server, the 409 is really the 3-photo cap or a verified bean, and the photo shows as sent although the server did not store it.
  - `LabelPhotoUploadModel` holds the photos of a saved, unverified bean: at most 3, each written off the main actor to the account's folder `Application Support/LabelPhotos/<account id>/` (`LabelPhotoFolders`, `LabelPhotoFileStore`; excluded from backups, `.completeFileProtection`; a failure to exclude it is logged with a fixed message) and uploaded in an unstructured task. A file is deleted after the 204; at once for a rejected, refused or removed photo; when the saved-bean screen goes away (`ScanFlowView` calls `BeanEntryModel.releaseLabelPhotos()`), for photos not uploading then and for the others when their upload ends; and when the model is freed (`deinit`, and a task that finds its model gone). `SyncHost` deletes an account's screen photos when its store is closed (sign-out, an ended session, another account) and, at every sign-in and app start, every other account's screen photos and the account's files older than a day; queued photos (M2-T25) stay with their store (see "Offline scan and pending beans"). `BeanEntryModel` creates the model once an unverified bean is saved while someone is signed in (`LabelPhotoAccount`) and hands it the form's photo, which starts uploading at once; a verified bean takes none.
  - `LabelPhotoUploadSection` is the section in `BeanDetailView` after the save: each photo with its state, Try Again, Retake or Remove, and "Add Another Photo" (3 taps: the button, the shutter, Use Photo) while fewer than 3 are there.
- Tests draw their images with CoreGraphics: `LabelPhotoEncoderTests` (sizes, `FFD8` and at most 8 MiB, a marker-level check against the rules of `jpeg.ts`, no EXIF, GPS, TIFF or XMP from inputs that carry them, every orientation, the quality loop and its floor) and `LabelPhotoDraftTests` (the draft states, availability, the UIKit orientation mapping). `PresignedLabelPhotoPostTests` (the URL and field checks, the exact multipart layout, no token), `LabelPhotoUploaderTests` (a fake API and a stub S3 transport: every status path, the file deleted after the 204, the live `APIClient` sending the token to the API only) and `LabelPhotoUploadModelTests` (3 photos at most, each outcome, retry and retake, the hand-over from `BeanEntryModel`, files deleted on release, on a freed model and by an upload that outlives its model) and `LabelPhotoFoldersTests` (one folder per account; sign-out, account switch and app start through `SyncHost`; another account's folder untouched by a sign-out). A real HEIC capture and a real upload to dev are checked in M2-T34.

## Local store

`Store/` (M2-T15) is the SwiftData copy of the user's own data (docs/04, Offline). `SyncHost` (M2-T16) opens the signed-in account's store; M2-T17 and M2-T18 add the pull and the screens.

- One store per account (ADR 0020). `StoreAccount` gives the store a stable account id: the same account always has the same one, and no two accounts share one. The signed-in account's is M2-T11's `AccountID`, already the lowercase hex SHA-256 of the id token's `sub`; `Store/AccountID+StoreAccount.swift` makes it a `StoreAccount`. The file is `Library/Application Support/Accounts/<sha-256 hex of the stable id>.store`: hashing again gives every id a fixed-length, file-safe name. An empty id throws. `AccountStore.open(for:)` opens only that file, with CloudKit off; `AccountStore.inMemory()` is a new empty store for tests and previews.
- `CupmarkSchemaV1` (`VersionedSchema` 1.0.0) holds `StoredBean`, `StoredShelfEntry`, `StoredBrew`, `StoredRecipe` and `StoredProfile` (and `OutboxOperation`, M2-T16). `CupmarkSchemaV2` (2.0.0, M2-T25) lists the same model types unchanged and adds `QueuedLabelPhoto`. `CupmarkSchemaV3` (3.0.0, M2-T26) adds `grinderID` and `grindSetting` to `StoredBrew` and `StoredRecipe`, so it holds its own copies of `StoredBean`, `StoredShelfEntry`, `StoredBrew` and `StoredRecipe` (the relationships name the brew), and shares the profile, the outbox and the label photo queue with the earlier versions. `CupmarkMigrationPlan` has a lightweight stage from 1 to 2 and one from 2 to 3, so a store of either version on a development device opens with its data and outbox (`StoreMigrationTests`, which writes the old stores with the old models). A new version adds `CupmarkSchemaV<N>`, a stage, and moves the type aliases of the models it changes.
- Every model has `localID` (the only `@Attribute(.unique)`), `serverID` (nil until the server has it; the profile has none, the API gives it no id), `vocabularyVersion` and `syncStateRaw`, a `SyncState` raw value (`synced`, `pending_create`, `pending_update`, `pending_delete`). Bean to shelf entry to brew are relationships with inverses.
- Vocabulary values are stored as contract ids (`methodID`, `bagSizeID`, ...) and read through the `Vocabulary` enums: an unknown id reads as nil and is kept. A rating is one JSON blob of ids (`RatingValues`: score by criterion id, level by dimension id, note ids), so no criterion or note list is written in Swift. Converting to an API type (`apiInput()`, `apiParameters()`, `apiRating()`) throws `LocalStoreError.unknownVocabularyID` instead of sending an unknown id, `missingServerID` while a referenced item has no server id, and `conflictingWaterTemperature` if both temperature columns are set. A rating is stored with `setRating(_:)` (or `apply(_:)`), which throws `nonFiniteScore` for a NaN or infinite score instead of dropping the rating. `apply(_:)` and the `init(_:)` from an API type take server values.
- Writes save at once. A local edit of a synced item makes it `pendingUpdate`; `markDeleted` takes only `LocalDeletable` models (not the profile). Deleting an item the server never had removes it, any other becomes `pendingDelete` and is hidden. A shelf entry with brews cannot be deleted (ADR 0012). A bean is a local copy with no server delete: it is removed at once, but never while a shelf entry still names it (`beanHasShelfEntries`). Lists: `brewsNewestFirst()` (by `brewed_at`, kept in whole milliseconds), `shelfEntries()` (latest purchase first), `recipes()`.
- **Failed writes** (M2-T35, ADR 0025 Addendum M2-T35). `ModelContext.rollback()` does not restore an attribute changed on a model that was already saved, so a failed edit would stay in memory with nothing queued and the next unrelated save would store it unsent. A failed `AccountStore.save()`, and a throw inside `AccountStore.write { }`, call `discardUnsavedChanges()`: every model the context lists as changed or deleted takes again the values the store holds for it, read through a fresh `ModelContext` on the same container, then the context rolls back (inserts and deletes). The disk is the snapshot, since no write leaves anything unsaved. `SavedValuesRestorable` (`Store/AccountStore+Write.swift`) lists, per model, every stored property it puts back with its key path, to-one and to-many relationships included; a test checks that no name and no key path is listed twice (SwiftData does not make the schema's key paths public). Writes that change a model before a call that can throw run inside `write { }`: the screen models' saves, `addShelfEntry`, `addBrew` (M2-T36), `setProfile`, `markUpdated`, `markDeleted`, the pending-bean answers, `addOfflineBean`, `redo`, `discard`, the pull's merge and the engine's question and look-up steps; the engine also discards before it saves a retry. Writes nest (M2-T36, ADR 0025 Addendum M2-T36): only the outermost `write` discards; an inner one just runs its body. An inner write's error caught inside the outer write still stores nothing: the outer write's later saves and its end throw `WriteNestingError.innerWriteFailed`. After the rollback the relationships are checked against the store once more and set where they differ (to-one first, then the exact to-many sets, never appended; a saved target is resolved from the context before any fetch, and one that cannot be found is left as it is, never replaced by nil, with an `assertionFailure` in debug), since a failed `ModelContext.save()` has already run the delete rules and a rollback of two deleted models that point to each other did not bring the relationship back. Then the context's pending changes are processed and every restored model is fetched again by its key; one a fetch still misses (after a second try) raises an `assertionFailure` in debug and a fixed fault message, since after a real failed save the first fetch once missed a pending bean the store has. If the store cannot be read while discarding, the model is only rolled back, with an `assertionFailure` in debug and a fixed `os.Logger` message. `AccountStore.willSave` is the tests' hook to make a save fail; a failure of `ModelContext.save()` itself is tested on a store opened with `allowsSave: false` (a uniqueness violation is an upsert in SwiftData, not a failed save).
- `BrewDerivedValues` is the one place for derived values: ratio `water_g / (dose_dg / 10)` (ADR 0004), and days since roast from `roast_date` to the day `brewed_at` falls on in the device calendar's time zone, counted on calendar days, so a daylight saving or time zone change never shifts it by one.
- Tests: `AccountStoreTests`, `StoredValuesTests`, `StoreLocationTests` (including two accounts on disk), `BrewDerivedValuesTests` and `FailedWriteTests` (each write site: a write that throws after changing a saved model leaves it as it was and queues nothing, also after the next unrelated save, read back from disk), with fixtures in `CupmarkTests/Support/StoreFixtures.swift`, whose ids are all valid contract ids (ULIDs).

## Sync outbox

`Store/Outbox.swift` and `Sync/` (M2-T16, ADR 0025) send the local writes to the API. docs/05, Client sync, has the rules in short.

- `OutboxOperation` is a model of `CupmarkSchemaV1` (added before any release, so no migration): `sequence`, resource and action (`create`, `update` or `delete` of a bean, shelf entry, brew or recipe; `update` of the profile; since M2-T25 also `look_up`, `await_confirmation` and `await_description` of a pending bean, see "Offline scan and pending beans"), the item's `localID`, `attemptCount`, `nextAttemptAt`, `sentWithoutAnswer`, and `parked` with a `parkReason`. Every model also has `syncIssueRaw` (`SyncIssue`: `rejected`, `bean_change_reverted`, `delete_restored`), the flag the screens show (M2-T18).
- `AccountStore`'s writes keep their API and add the operation before their one save: `addBean`, `addShelfEntry`, `addBrew`, `addRecipe` (with `syncState: .pendingCreate`, the default), `setProfile`, `markUpdated` and `markDeleted`. An edit is not queued again while a create or update that was not sent yet carries it (the body is built when an operation is sent). Deleting an item whose create may have reached the server (`sentWithoutAnswer`) keeps it as `pendingDelete` and queues a delete after the create; otherwise a never-sent item goes at once with its operations. A bean is local only and has no delete route.
- `SyncEngine` (main actor, the same context as the screens) sends the lowest sequence that is not parked, one at a time; a retry holds the queue. A shelf entry's bean and a brew's shelf entry are read through the relationship when the body is built, so the request carries the server id the referenced item has by then; if that item never got one, the operation is parked (`missingReference`). Before each request it asks `AuthSession.isSignedIn(as:)` and stops if another account (or nobody) is signed in.
- Answers: 2xx stores the server id and, when nothing later is queued for the item, the server values. 429, 503, other 5xx and transport failures back off with `SyncBackoff` (2 s doubling to 300 s, equal jitter); `drain()` returns `.waiting(until:)`. `unauthorized` (after `APIClient`'s one refresh and retry) returns `.signInRequired`, keeps every operation and calls `onSignInRequired`. 400 parks (`rejected`) and flags the item; so do a 404 on a create and an answer that breaks the contract. 404 on a delete is done. A 404 on a replace is followed by a `GET` of the item: 404 removes the local item, 200 parks the operation (`rejected`: the body named a bean or shelf entry the server refuses) and keeps the item, a transport failure or 5xx retries. 409 on a shelf delete restores the entry (`delete_restored`); 409 on a shelf replace gets the entry, relinks the server's bean (fetched if not cached), flags `bean_change_reverted` and sends the other values again. 409 on a bean create adopts the catalogue bean for the barcode.
- `sentWithoutAnswer` is saved before each request. If a create comes back without an answer that says the server did nothing (a transport failure after a connection was made, 5xx, the app ended), the next attempt first lists the resource (counted as an attempt, so it backs off) and adopts a server item with no local counterpart that matches the body last sent (`sentBody`), not the current values: a brew with the same `shelf_entry_id` and `brewed_at`, a shelf entry with the same values, a recipe with the same parameters.
- `SyncHost` (`CupmarkApp`, `.syncHost(_:auth:)`) switches with the signed-in account: it stops the old engine, opens the new account's store and starts its engine with the app's one `APIClient`. Sign-out stops the engine; a sign-in-required stop from the current engine signs out, but only while that account's session is still saved. Screens edit drafts and write them through `AccountStore`, since the engine's saves save the shared context. A local save wakes the engine (`AccountStore.onSave`).
- Tests: `SyncEngineTests` with `FakeSyncServer` (`CupmarkTests/Support/FakeSyncServer.swift`, an in-memory API over `StubURLProtocol`), a `TestClock` and a fixed jitter: each status rule, the order, the rewrite across bean, shelf entry and brew, the adoptions, an on-disk store reopened with its queue, stopping and the account check.

## Pull and reconcile

`Sync/Puller.swift` (M2-T17) brings the server's copy to the device, so a new device ends with a full copy and an edit or delete on another device shows here. docs/05, Pull, has the rules in short.

- When: `SyncHost` asks for a pull on sign-in (`switchTo(_:)`), when the scene becomes active (`sceneBecameActive()`, which also kicks the engine), and after a drain that finished an operation (`SyncEngine.finishedOperations` changed). The pull runs in the engine's idle slot (`SyncEngine.onIdle`) once the outbox is empty, so the local writes go first and `drain()` answers `.busy` while a pull runs. A pull that only follows a drain waits until 30 s after the last completed pull (`drainPullInterval`) and stays due until then; sign-in and foreground always pull. A failed pull is asked for again and runs at the next trigger.
- What: every page of `GET /shelf`, `/brews` and `/recipes`, then `GET /profile` (404: no profile yet, none is created), then `GET /beans/{bean_id}` for each shelf bean (of the server's or the device's entries) that is not cached or is not verified. Nothing is written until every request has answered; the merge then runs on the main actor without a suspension and saves once.
- Merge: a server item with no local item is inserted as synced, with no outbox operation. A synced local item the server no longer lists is removed, except when that list had an undecodable item (it may be that one) and except a shelf entry that still has brews on the device. An item that is not synced or has any operation in the outbox, parked ones included, keeps its local values. Any other takes the server's values; beans are only added or refreshed, never removed.
- `PullReport` counts what happened. `undecodableItems` (from `AllPages.undecodableItems`, plus a `GET /beans/{bean_id}` or `GET /profile` answer that does not decode, treated like a 404 for a bean and as skipped for the profile, never as "no profile") and `unresolvedItems` (a bean or shelf entry the device could not get) make `skippedItems`, which `SyncHost.lastPull` exposes for a later note on screen. A 401 after the refresh stops the engine and asks for sign-in, like a drain.
- Tests: `PullerTests` with `FakeSyncServer`, which pages its lists (`limit`, cursor `o<offset>`) and serves `GET /profile`: 250 brews over three pages into an empty store, insert, update, remove and keep-pending, bean fetch and refresh, an undecodable item, a profile 404, a failed request that writes nothing, and the host's order (outbox, then pull), the busy drain, the foreground pull and sign-in required.

## Offline scan and pending beans

M2-T25 makes docs/04, Non-functional (Offline: "Scan, brew and rate work offline and sync later") hold for a scan. ADR 0025, Addendum (M2-T25), has the rules.

- **Scan offline.** When the lookup cannot answer (`.pickList(.unavailable)` or `.limitReached`), `LookupFallbackView` offers "Add to Shelf Now" (`LookupModel.keepForLater()`, state `.keptForLater`), which opens the shelf entry form at once (`AddToShelfBar(scanned:presentsAtOnce:)`, `ShelfEntryEditorModel.Mode.addScanned`). Saving it saves the pending bean (`AccountStore.pendingBean(barcode:)`: the barcode, no server id, an outbox operation `look_up`) with the entry in one save; cancelling stores nothing. A barcode the device already has a bean for reuses it. Brews are logged on the entry as on any other.
- **A pending bean lives for its entries.** `markDeleted` of its last shelf entry, and moving that entry to another bean (`ShelfEntryEditorModel`), remove it with its operations and queued photos (`dropPendingBean`); the engine drops one it finds without a live entry instead of looking it up; questions skip beans without an entry.
- **Describe offline.** `BeanEntryModel.save()` saves the bean on the device when the API cannot answer and the flow has a store: `AccountStore.addOfflineBean` queues the `create` (a plain `POST /beans` later; a 409 for its barcode adopts the catalogue's bean, so it is created without asking, and it never gets an Open Food Facts name or image) and the form's label photo, in one save. A bean the device already has takes the picks while its create is unsent; one the server has cannot, and the screen says so (`picksNotKept`). A photo that cannot be written saves nothing and shows `photoNotSaved`.
- **Resolve.** `SyncEngine` sends `look_up` as `GET /barcodes/{barcode}`: a bean is used (`adoptBean`, which also merges a duplicate local copy and moves its queued photos). A 404 asks `GET /barcodes/{barcode}/open_food_facts`: a hit is kept on the bean (`holdOpenFoodFactsProduct`) and the operation becomes `await_confirmation`; a miss becomes `await_description`; a 409 retries the catalogue later. No network, 5xx and 429 make the look-up wait (`SyncBackoff`, or `SyncEngine.lookUpLimitWait`, an hour, for the daily cap of the Open Food Facts route).
- **Order.** `AccountStore.nextOutboxOperation(at:)` skips a bean whose look-up waits (until `nextAttemptAt`, or for the user) and every operation that needs it; everything else keeps its order. An operation whose shelf entry or bean has no server id and still has its create or look-up queued gets that operation sent first, whatever the sequences (`OutboxDependencies`), so an earlier entry moved to a pending bean is not parked. A delete never waits. The bodies are built when sent (ADR 0025), so nothing is rewritten. The engine rests no longer than the next look-up attempt.
- **Questions.** `ShelfScreen` opens `PendingBeansScreen` once each time the app comes to the foreground while a question waits, only while the shelf itself is on screen with none of its sheets up (`isOnScreen`, set on appear and disappear, so a pushed screen and whatever it presents block it); a "Scanned Bags to Check" row opens it at any time. A hit shows `OpenFoodFactsConfirmView`: Confirm (`confirmOpenFoodFacts`, with the optional picks) creates the bean; "Not my coffee" (`rejectOpenFoodFacts`) drops the product and asks for a description. A description (also after a miss, docs/04 F1 step 4) is `BeanEntryScreen` with a `BeanEntryModel` in its describing mode (`describing:`): Save writes the picks and the photo to the bean (`describePendingBean`) and sends nothing itself, never `POST /beans`, also without a store; "Skip" (`skipDescription`) creates the bean from its barcode. "Later" leaves it waiting. Until it is settled the shelf shows the bean without the Open Food Facts name (`StoredBean.showsOpenFoodFactsText`) and a note per row (`PendingBeanState`).
- **Label photos.** `QueuedLabelPhoto` (schema 2) names the bean by local id and the JPEG by file name in the account's queue folder `LabelPhotos/<account id>/Queued/`, and holds the encoded `LabelPhotoUploadJob` (now `Codable`; `ResourceID` encodes as its string). `LabelPhotoQueue` runs in the engine's idle slot (`SyncHost`, before the pull): a photo waits until its bean has a server id, then `LabelPhotoUploader` runs it; completed, rejected and "no more photos" end it with its file, the daily cap waits 6 hours, other failures back off, and the stored job resumes where it stopped. A verified or removed bean drops its photos.
- **Folders and sign-out.** Queued photos belong to the account's store, which stays on the device after a sign-out (one store per account, ADR 0020), so they stay with it: a sign-out deletes the screen photos and the queued files the store does not list (none if the store could not be read); a sign-in deletes other accounts' files but their queue folders, and the account's queued files its store does not list. `removeFolder(of:)` still deletes everything of an account.
- Tests: `PendingBeanSyncTests` (scan, shelf and brew offline through `LookupModel` and `ShelfEntryEditorModel`, then a known bean, a hit confirmed, a hit rejected and described, a miss described, a miss skipped: each time the brew ends up on the server under the entry, which names the right bean; a described photo queued; a cancelled form, a removed last entry and the engine's drop; questions skipping beans without an entry; other writes and deletes going out while a bean waits; an earlier entry moved to a pending bean; the daily cap; pick-list beans saved offline, a second description and one of a catalogue bean; a restart), `LabelPhotoQueueTests` (the job round trip, waiting for the server id, every outcome, resuming, an offline entry's photo uploaded after the drain, the merge), `LabelPhotoFoldersTests` (queued files kept or removed by the store's list) and `StoreMigrationTests`. The `SyncHost` tests of `SyncEngineTests` and `PullerTests` use a temporary `LabelPhotoFolders` root.

## Shelf

`Shelf/` (M2-T18) implements F1 step 5 and the screens ADR 0025 left to it. Screens edit drafts (plain values) and write them through `AccountStore`, never a live model, since the sync engine saves the same context.

- **Root.** When signed in, `RootView` shows `ShelfRoot`, which waits for `SyncHost` to open the account's store (an error if it cannot), then `ShelfScreen`: a "Sync Issues" row while there are any, "Scan a bag" (pushes `ScanFlowView` with a `ShelfAddContext`), and the shelf list.
- **List.** `ShelfModel` reads `AccountStore.shelfEntries()` (latest purchase first, removed entries hidden), so it works offline. `AccountStore.save()` posts `AccountStore.didSaveNotification` after every save (screen writes, the engine and the pull alike), and the screens read again on it; the shelf also reads again when the app comes to the foreground, so days since roast move on. Each row (`ShelfRow`) shows the bean (`ShelfBeanSummary`: the Open Food Facts name and brand with `Text(verbatim:)`, or else the attribute labels, operator's value first, or "Bean without details"), the roast date, days since roast (`StoredShelfEntry.daysSinceRoast(on:)`, through `BrewDerivedValues.daysSinceRoast`, to today in the device calendar) and the brew count (`liveBrewCount`: brews on the device that are not `pendingDelete`).
- **Adding.** A found, confirmed or created bean (`LookupScreen`, `BeanEntryScreen`) gets "Add to Shelf" (`AddToShelfBar`), which opens `ShelfEntryEditorScreen` in a sheet: purchase date (a date picker, today by default), an optional roast date behind a toggle, bag size and price band (pick lists from the vocabulary). Save caches the catalogue bean (`AccountStore.catalogueBean(_:)`, synced, no outbox operation) and adds the entry with `addShelfEntry` in one save, which queues `create shelf_entry`. After the sheet closes, the flow pops back to the shelf. `ShelfEntryDraft.input(beanID:)` is the `ShelfEntryInput` the draft maps to; the outbox builds the body from the stored entry when it is sent. An id the bundled vocabulary does not know is kept unless the user picks a value.
- **Entry.** Tapping a row opens the same form for the stored entry: the dates, bag and price, another bean (`ShelfBeanChoiceList`, the beans on the device) and "Remove from Shelf" (`markUpdated` and `markDeleted`). While `brewCount > 0` the bean change and the removal are disabled, with the localised reason below them (D14, ADR 0012); `save()` and `delete()` count again before they write, so a brew added meanwhile is respected.
- **Sync issues.** `AccountStore.syncIssues()` lists every item with a parked operation, in queue order (a refused create, change or removal, also a 404-then-200 on `PUT` and a refused delete whose item is still `pendingDelete` and hidden elsewhere), then every flagged item with nothing parked (`bean_change_reverted`, `delete_restored`, an old `rejected`). `SyncIssuesScreen` offers:
  - parked: "Try Again" (`redo(_:)`: the operation goes back at its own place with a fresh attempt count, the flag is cleared, and a parked create, only a create, of the bean or shelf entry it references is redone with it) and "Discard" (`discard(_:)`: a refused create removes the item, refused while brews still reference the entry or shelf entries still name the bean; a refused update or delete drops the parked operation and the item's state follows what still waits, a waiting delete keeping it `pendingDelete`, otherwise synced, and the screen asks `SyncHost` for a pull, so the server's values come back and a refused delete brings the item back; a stale row whose operation is no longer parked only clears the flag);
  - a flag only: "OK", which clears it.
- Tests: `ShelfEntryDraftTests` (the mapping to `ShelfEntryInput`, picker dates in several time zones, days since roast across midnight and a daylight saving change, unknown ids kept), `ShelfModelTests` (adding offline with one queued create, reusing the cached bean, the rows, and the disabled bean change and removal while the brew count is above 0, also when a brew arrives while the screen is open, and a brew removed on the device not counting), `SyncIssuesTests` (redo and discard against the real `SyncEngine` and `FakeSyncServer`: 400 on create, update and delete, 404 then 200, 409 on delete and on a bean change, a parked reference), `BeanAttributeFieldTests` (the fields are exactly `API.BeanAttributes.propertyNames`), and 401 tests in `LookupModelTests` and `BeanEntryModelTests`. `scripts/ios-scripts.test.mjs` checks that Open Food Facts name and brand reach views only through `Text(verbatim:)`, also across lines and in `LabeledContent`, `Label`, `Button`, `navigationTitle` and the accessibility labels, and that the shelf has no typed text and writes only through `AccountStore`.

## Brew form

`Brew/` (M2-T19) implements docs/04 F2. Since M2-T26 it applies the method field rules of vocabulary v3 and has the grinder and its grind setting (see "Method fields and grinder" below).

- **Start.** A brew starts from a shelf entry: swipe a shelf row to the right ("Log a Brew", also a VoiceOver action) or use the button at the top of the entry's screen. Both open `BrewFormScreen` in a sheet.
- **Fields.** Method: a pick list, required; it starts as the method of the entry's latest brew, so a repeat brew needs no pick. Dose, water or yield and the normalised grind: steppers. Water temperature: a pick list of "Not set", "Heated" (then a stepper in °C) and the vocabulary's `water_temp_special` values (`cold`); `API.WaterTemperature` holds one of them, so a temperature and `cold` are never both set. Water type and milk: pick lists. Everything but the method is optional, and each stepper has a clear button. Nothing is typed.
- **Ranges.** `BrewNumberField.range` is the only place a stepper's bounds and step are read, from `Vocabulary.Ranges` (`doseG`, `waterG`, `waterTempC`, `grindNormalised`). `BrewDraft.setValue(_:of:)` clamps and snaps every value to its range; the dose is stepped in grams and stored as `dose_dg` (18.5 g is 185, ADR 0004). A field that is not set starts, on its first tap, at the latest brew's value of that field (same method first, then any brew), or else at the step nearest the middle of its range. The view writes no bound or step (`scripts/ios-scripts.test.mjs` checks it).
- **Derived values.** The ratio (`1:16.2`, through `BrewDerivedValues.ratio`, in the device locale) and days since roast (to today, the day the brew is recorded) follow the values as they change.
- **Save.** `BrewFormModel.save()` records `brewed_at` from the device clock, makes a `StoredBrew` with `vocabulary_version` = `Vocabulary.version` and adds it with `AccountStore.addBrew`, which queues `create brew` in the same save, so it works offline. The request names the shelf entry by the server id it has when the operation is sent, so a brew on an entry that is still waiting for its own create goes out after it. A saved form saves nothing more; a failed save changes nothing, the entry included (`AccountStore.write`), and can be tried again.
- **Method fields and grinder** (M2-T26, ADR 0021, D13). The rules and scales are the generated ones (`Vocabulary.Method.allows(_:)`, `Vocabulary.Grinder.scale`); no method, field, grinder or scale is written in Swift.
  - `BrewDraft` keeps the rules by construction: `method` has a `didSet` that clears every field the new method does not allow (`BrewDraft.allows(_:)`, `visibleFields`), a setter ignores a field the method does not allow, and `parameters` is passed through `API.BrewParameters.conformingToMethodRules()` once more (`Brew/BrewParameterRules.swift`), so a `BrewInput` never holds a field the server answers with 400. While no method is picked only fields without a rule are shown, and nothing is cleared (nothing can be sent). The form hides a field with `BrewFormModel.shows(_:)`; the temperature picker offers "Heated" only where `water_temp_c` is allowed and the `cold` value only where `water_temp_special` is, and is hidden where neither is (moka pot, cezve).
  - **Grinder.** An A to Z pick list (`IndexedPickListRow`, no search field) with a "Recent" section of the grinders of the latest brews (`BrewFormModel.recentGrinders`, at most `recentGrinderLimit`). Labels come from `contracts/i18n` like every other vocabulary value. It includes `pre_ground`, `other` and the grinders without a scale.
  - **Grind setting.** A stepper on the grinder's own scale (`BrewDraft.grindSettingRange` is `Grinder.scale`, with its minimum, maximum and step), shown only while the grinder has a scale. A value is snapped onto the scale; the first tap starts at the setting of the latest brew with the same grinder, else the middle of the scale. ## Export and local data

`Export/` and `Settings/` (M2-T30, ADR 0017, docs/05 Security, Export). The shelf has a "Settings" row (`SettingsRoute`, `SettingsScreen`), two taps from the shelf to Export.

- **Export.** `ExportModel` (`@MainActor`, `@Observable`) runs, on the "Prepare Export" button:
  1. `ExportOutbox.drain` (`SyncEngine.drain()`; a `.busy` answer, because the engine's own loop is draining, is asked again up to `busyRetries` times a second apart; a backing-off, stopped or sign-in-required engine is not waited for);
  2. `GET /export` (`APIClient.exportData()`, `ExportSource`), with the token and no query or body;
  3. the bytes, unchanged, to `<tmp>/CupmarkExport/<random>/cupmark-export-<YYYY-MM-DD>.csv` (`ExportFileStore`; the day in the device calendar; `.completeFileProtection`). `ExportScreen` offers it with `ShareLink`;
  4. the file and its folder are deleted when the user taps "Done, Delete the File", when the screen goes away, at the next export and at app start (`CupmarkApp.init`). Building a model deletes nothing, since SwiftUI may build one more than once.
- **Pending changes.** After the request, `ExportOutbox.pendingChanges` counts the outbox operations (parked ones too, since they are not on the server either). If any are left, or the outbox cannot be read, the file is still offered, with a note that those changes are not in it.
- **Errors**, each a localised message and no file: a transport failure is "offline"; a 500 (an export over 5 MiB, docs/05) is the size-limit message; a 401 after the refresh asks to sign in again; a 429 and any other failure (503, other 5xx, an unexpected answer) have their own text; a file that cannot be written has one too. Cancelling ends idle.
- **Other accounts' data on the device** (from the M2-T16 review). After an account is deleted on another device, this device keeps that account's store, outbox and queued label photos. "Remove Data of Other Accounts" in Settings (`LocalDataRemover`, `LocalDataModel`) deletes every store file `<64 hex digits>.store` (and `-wal`, `-shm`) whose name is not the signed-in account's, and the label photo folders of other accounts (`LabelPhotoFolders.removeFolders(exceptOf:)`), after a destructive confirmation that says unsent changes are lost. The signed-in account's data and files of any other name are never touched. Decision (lead, ADR 0014 rule for open decisions): there is no automatic removal on the tombstone 401. After `APIClient`'s refresh a 401 looks the same for a deleted account and for a revoked or broken session of a live one, and removing the store of a live account would lose unsent changes. Since M2-T31 the sign-in screen gives the reason (see "Account deletion"); account deletion on this device removes its own store.
- Tests: `ExportTests` (the request, the file name across time zones, bytes written unchanged including non-UTF-8 bytes, deletion, the order drain then request then pending count, the pending note, busy retries, the real engine sending the outbox before `GET /export`, a parked change still pending, 500, offline, 401, 429, 5xx, a file that cannot be written, a retry) and `LocalDataRemoverTests` (other accounts' files go, the own and unrelated files stay, real stores with an outbox, label photos, name shapes).

## Account deletion

`AccountDeletion/` (M2-T31; docs/04 Non-functional, account deletion in the app; ADR 0017 and its Addendum; ADR 0031; contracts `deleteAccount`).

- **Where.** Settings, then "Delete Account" (`AccountDeletionDestination`, which reads the app's `AccountDeletionModel` from the environment, so no file under `Settings/` touches the API client). Two steps, buttons only, and both say what is deleted (the data, the label photos of unverified beans, the sign-in): the screen's list with "Continue to Deletion", then a confirmation dialog with "Delete Account". From the shelf: Settings, Delete Account, Continue to Deletion, Delete Account (4 taps).
- **The record.** `AccountDeletionModel.start()` first saves `AccountDeletionRecord` (`requested`, the account, the accounts whose local data goes) in the Keychain (`KeychainAccountDeletionStore`: service `app.cupmark.Cupmark.deletion.<stage>`, account `account-deletion`, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`). If that fails, nothing is stopped or sent (`couldNotStart`). The record lives outside the store and Application Support, survives a reinstall like the sign-in, becomes `serverDeleted` after the 204 and is removed last. `CupmarkApp` builds one model for the app; `AuthGate` reads the record before restoring the sign-in, and `AccountDeletionModifier` resumes a recorded deletion at launch, on every account change and on return to the foreground.
- **Nothing more is sent.** The sync host is held (`SyncHost.holdForAccountDeletion()`: the engine stops, the store closes, and no label photo is deleted), and while a record exists `SyncHost.switchTo(_:)` opens no store for any account and `AuthSession.maySend(as:)` is false; the engine, the pull, the label photo queue and the screen uploads (`LabelPhotoAccount.live`) ask it before every request. While the record exists `AuthGate` shows `AccountDeletionProgressView` instead of the signed-in screens, without the sign-out button.
- **Requests.** Each run (start, every resume) refreshes the token of the account it targets (`AuthSession.refresh(for:)`), then sends `DELETE /account` with that account's token only (`AccountTokenProvider`); a resume during a run makes another run follow it. 500, 429, 503, other failures and network failures, of the refresh too, back off with `SyncBackoff` and retry until a 204; "Try Now" and the foreground retry at once. Later attempts of a run keep the token, so a retry after a deletion the server finished still gets its 204 (ADR 0017, Addendum). Until the 204 the user stays signed in: nothing signs out, discards a token or deletes a file.
- **Refresh fails** (`unauthorized`, ADR 0031). A session that ended itself (`invalid_grant`) shows the sign-in screen; a session still saved offers "Sign In Again" (`AuthModel.signInAgain()`, no sign-out; a failure is shown). Both screens warn: "Sign in with the account you asked to delete to finish deleting it. If you sign in with a different account, Cupmark asks you before it deletes anything." The same account goes on at once. A different account (the app cannot tell a new Cognito user for the same Apple ID from another Apple ID) stops before any request (`confirmDifferentAccount`): "Delete This Account" moves the record to it and deletes it, and the final note says that this account was deleted (`otherAccountDeleted`); "Sign Out" signs out of that session only and keeps the record (nothing is deleted and no account request is sent; the sign-out revokes the new session's token). "Delete This Account" only deletes the account the prompt was worked out for (`confirmationAccount`). No run starts while a sign-in is under way (`AuthModel.isSigningInAgain`), and right before `DELETE /account` the saved sign-in is checked again and the request takes only the target's token (`AccountTokenProvider`, `AuthSession.accessToken(for:)`), so a sign-in that lands mid-attempt sends nothing and shows the prompt. The prompt is derived from the saved sign-in and the record, so a restart shows it again.
- **Unreadable record.** A record that cannot be decoded is kept (`AccountDeletionStoreError.unreadableRecord`) and holds sync; the progress screen asks before it deletes the signed-in account (`confirmUnreadableRecord`).
- **After the 204** (`AccountLocalData`, then the sign-out, then the record): each listed account's store files (`<stem>.store`, `-wal`, `-shm`: the data and the outbox) and label photo folder `LabelPhotos/<account>/` with its `Queued` photos; the cached catalogue images and export files; `AuthModel.signOut(reason: .accountDeleted)` (the Keychain sign-in), and the sign-in screen says "Your account and its data were deleted."; then the record. Each step is safe to repeat, so a crash after the 204 finishes at the next start without another request, provided the `serverDeleted` save succeeded (otherwise see ADR 0031, point 6). `AuthGate` resumes after restoring the sign-in, so a cold start signed out also finishes the cleanup.
- **Tombstone 401** (from the M2-T16 review). When sync asks for sign-in, `SyncHostModifier` calls `AuthModel.signOutAfterServerRefusal(of:)`, which signs out with `Failure.signInRequired` ("This account was deleted, or its sign-in ended. Please sign in again."); the lookup's `SignInAgainButton` uses the same note. The store stays (M2-T30's decision).
- Tests: `AccountDeletionTests` against the real `AuthModel`, `AuthSession`, `APIClient`, `SyncHost` and on-disk stores, with `FakeTokenEndpoint`, a fake web sheet, `FakeAccountDeletionStore` and a `StubServer` kept alive for the whole test: three 500s then a 204 (one refresh, four `DELETE /account` and nothing else, one sign-out, the store files, photos, images and export gone, the record last); no sign-out on a 500; resuming after a restart (no store opened, a refresh, then the 204); the refresh-failure path with a new account (stopped before any request, deleted once after the tap, the other-account note) and with the same account (no prompt); "Sign Out" on the prompt keeping the record and sending nothing; a restart showing the prompt again; "Sign In Again" as another account and a failed one; a resume during a run; a sign-in landing after the refresh or just before the request's token, sending nothing; a resume during "Sign In Again" starting no run; "Delete This Account" refused after the session changed; an undecodable record (and a real Keychain item kept); 429, transport, 503 and 502 retried; an offline refresh retried; nothing sent after a kick, the foreground or an account switch; a record that cannot be saved; a crash after the 204 and after the sign-out; `AccountLocalData` leaving other accounts' data; the held host; `maySend`; the record's coding and a real Keychain round trip (skipped without a Keychain). `AuthModelTests` covers the notes and `signInAgain()`. `scripts/ios-scripts.test.mjs` checks on Linux: no typed text, no API client in any Settings file, the record saved before the hold and the first request, refresh before `DELETE`, the only sign-out after the local data and before the record, the host's hold and `maySend` in every live sender.

## Brew timer

`Brew/BrewTimer.swift` and `Brew/BrewTimerRow.swift` (M2-T21) implement the timer of docs/04 (Input model, F2 brew time) in the brew form, between the amounts and the water.

- **Start, Stop, Reset.** One button starts and stops; Reset sets the timer back and clears `brew_time_s`, so the readout and the saved value never disagree. A new Start after a Stop times again from zero, and the brew time already set is replaced only when that timing stops. Saving while the timer runs stops it first, so its time is saved. Nothing is typed.
- **Measured from the start instant.** `BrewTimer` keeps only the `ContinuousClock.Instant` it was started at, and the elapsed time is always `now - start`, never counted up by ticks. `ContinuousClock` keeps advancing while the device sleeps and does not follow wall-clock changes, so time in the background or with the phone locked counts. The clock is injected (`BrewTimerModel(now:announce:)`). A `TimelineView` redraws the readout while the timer runs.
- **Only in memory.** The start instant lives only in the open brew form, not in the store. If iOS ends the app while it is in the background, or the phone restarts, the running timing is lost and the brew time stays unset (this matters for long brews such as cold brew, which may run for hours). Persisting a wall-clock start with the draft is a possible follow-up; a `ContinuousClock` instant cannot be persisted across a restart.
- **Clamp.** Stop takes the whole seconds (rounded down) and moves them into `Vocabulary.Ranges.brewTimeS` and onto its step (`BrewDraft.brewTimeS(for:)`, `BrewDraft.brewTimeRange`, the only place the range is read). `BrewDraft.brewTimeS` is `private(set)`: apart from the copy of a stored brew, it is set only through `setBrewTime(seconds:)` and `setBrewTime(_:)`, which both clamp: a stop within the first second is the minimum, a timer left running past the maximum the maximum.
- **Readout and VoiceOver.** The readout is `m:ss` (`h:mm:ss` from one hour), in the device locale, in the large title text style, so it follows Dynamic Type; at accessibility sizes the buttons stack. VoiceOver reads it as "Brew time" with the time in words (`Duration.UnitsFormatStyle`) and treats it as updating frequently. Start, stop (with the brew time, through the format key `brew.timer.announce.stopped_with_time %@`) and reset are announced, queued after the tapped button's label. The announcements are `String` members of `L10n` (`String(localized:)`, the stop one a function whose interpolated parameter is `%@` in the key), which `scripts/check-ios-strings.mjs` counts as keys.
- Tests: `BrewTimerTests` (30 s with no tick in between counts as 30 s, the time read from the start instant, a second start, the range equal to the bundled one, the clamp at both ends and on whole seconds, the timed brew saved and a save stopping a running timer, reset while running and after a stop, a new timing, the announcements, the readout and the spoken time). `scripts/ios-scripts.test.mjs` checks on Linux that the timer reads its range from the vocabulary and the view reads none.

## Rating

`Rating/` (M2-T20) implements docs/04 F3: a brew is rated on the criteria of the bundled vocabulary, with optional intensities, flavour notes and buy again.

- **When.** Right after a brew: `BrewSheet` (opened by both "Log a Brew" entry points) shows `BrewFormScreen` until the brew is saved, then `RatingScreen` for it in its place; "Later" closes the sheet and leaves the brew unrated. Later: the shelf entry's screen has "Brews", `BrewListScreen`, the entry's brews newest first with rated or not, each opening its rating. A rated brew opens with its rating, so the rating can be changed.
- **Scores.** One slider per `Vocabulary.Criterion`, on `Vocabulary.Ranges.scale` (1 to 10) in its step (0.5), with the criterion's label and its question from contracts/i18n (`VocabularyStore.question`). A criterion without a score shows "Not set" with the slider dimmed in the middle; touching the slider sets it, also without a move. `RatingDraft.setScore(_:for:)` clamps and snaps every value onto the scale's half steps. Save is enabled only when every criterion has a score: `Scores` requires all of them. VoiceOver reads the label and the score, adjusts by one step, and gives the question as the hint.
- **Intensity.** One segmented control per `intensity_dimensions` entry with the `intensity_levels`, nothing selected until a level is picked, and "Clear"; a pushed list with "Not set" at accessibility text sizes. Optional: no level, no `intensities`.
- **Flavour notes.** Two levels: "Pick Flavour Notes" opens the `flavour_categories` in file order, each with its picked count, then the notes of a category. Up to `RatingDraft.maxFlavourNotes` (`Vocabulary.Constants.maxPicks`, `flavour_notes.max_picks`) can be picked, in the order picked and never twice; at the limit every note that is not picked is disabled, with a note. Picked notes are listed on the rating, and a tap removes one.
- **Buy again.** Optional, three states: not set, Yes, No. A segmented Yes and No with "Clear" (a pushed list with "Not set" at accessibility text sizes). Not set is nil and is not sent, so an untouched control never counts as "no" in the bean's buy-again share (F4). A stored nil opens as not set, a stored yes or no as that answer.
- **Repeat brews.** An unrated brew offers an earlier rating, copied into the draft only on that tap, then changed where the cup was different (`RatingFormModel.offeredRating`, ADR 0026 and its Addendum M2-T27): the newest rating of an earlier brew of the same shelf entry ("Start from the Last Rating of This Bag"); else of the same bean on any shelf entry ("... of This Coffee"); else, for a brew logged as a repeat of the last brew, the rating of the brew it copied ("Start from the Rating of the Repeated Brew"; `BrewSheet` passes `BrewFormModel.copiedBrewID` as `repeatedFrom`). A later brew's rating is never offered.
- **Save.** `RatingFormModel.save()` writes through `AccountStore.rateBrew`, which checks the rating (`RatingValues.apiRating()`: complete, known ids), stores it, raises the brew's `vocabulary_version` to the bundled one if it was older, and calls `markUpdated`, all in one save. A brew the server has gets `pendingUpdate` and one `update brew` (`PUT /brews/{brew_id}`), shared by later changes until it is sent; a brew whose create has not been sent keeps its one create, which then carries the rating. It works offline; a failed save changes nothing (`AccountStore.write`). Saving a rating unchanged writes nothing and queues no update.
- **Newer vocabulary.** A brew stored with a `vocabulary_version` above the bundled one opens its rating read-only, with a note to update the app, so a save cannot drop notes or intensities this build does not know.
- **Brew list.** "Brews" on the shelf entry is a value link (`BrewListRoute`) and its rows are value links (`BrewRatingRoute`), so a screen and its model are made only when one opens. Both destinations are registered at the shelf's stack root (`brewNavigationDestinations`, `Brew/BrewRoutes.swift`), never inside a pushed screen: a `navigationDestination(for:)` in a pushed view can be lost on a rebuild, and Back then showed an empty screen with a warning triangle (M2-T40). `scripts/ios-scripts.test.mjs` allows `navigationDestination(for:)` only in `ShelfScreen` and `BrewRoutes`.
- Nothing is typed, and no list, scale or limit is written in Swift: the views read them through `RatingDraft` and the generated enums (`scripts/ios-scripts.test.mjs` checks it).
- Tests: `RatingTests` (the mapping to `Rating` and its JSON, optional parts left out, buy again omitted when not set and sent as true or false, a round trip of a stored rating, unknown ids dropped, the scale equal to the bundled one, half-step snapping and clamping, the slider touch, every criterion's question in every language, the limit equal to the bundled `max_picks`, further picks refused and allowed again after a removal, an incomplete set of scores not saved by the model or the store, one queued update for a synced brew and its coalescing, the rating riding on an unsent create, an offline rating sent as `PUT` once online, the last rating of the bag, a removed brew, a failed save, and the brew list).

## Statistics

`Statistics/` (M2-T28, ADR 0027) shows the user's own statistics, computed on the device from the account's local store. It works offline, calls no route and writes nothing.

- **Where.** The shelf has "Statistics" under "Scan a bag", one tap from the shelf. It is a value route (`StatisticsRoute`), so the screen and its model are made only when it opens. `StatisticsScreen` reads at once on appearing and when the app comes to the foreground. After a save of the store (`AccountStore.didSaveNotification`) it calls `StatisticsModel.scheduleReload()`, which waits `reloadDelay` (250 ms) and restarts the wait on each further save, so a sync drain that saves once per operation causes one read.
- **Pure computation.** `StatisticsModel` turns the store's brews (`AccountStore.brewsNewestFirst()`) into plain `StatisticsBrew` values (time, method, the shelf entry's bean as a `ShelfBeanSummary`, the `RatingValues`, removed or not) and calls `PersonalStatistics.compute(_:now:calendar:)`, a pure function, so the tests need no SwiftData.
- **What.** Removed brews (`pendingDelete`) count nowhere; unrated brews count as brews, never in a score.
  - Brews: the total, the rated ones, and brews per ISO week for the last `StatisticsRules.weekCount` weeks, oldest first, the current week last. Weeks are ISO 8601 (Monday first, the first week has at least four days) in the device time zone (`PersonalStatistics.isoWeekCalendar(timeZone:)`), so a brew late on a Sunday stays in its week and the week number of the last days of December can be 53. A week without brews shows 0 once there are brews.
  - Taste profile: the mean of each criterion over the ratings that score it, in vocabulary order, and the same per method for each method with at least `StatisticsRules.minimumRatedBrews` rated brews. Methods with an id this build does not know count as brews only.
  - Flavour notes: the `StatisticsRules.topFlavourNoteCount` notes picked most often, a note counted once per rating; equal counts keep the vocabulary order.
  - Best method and best bean: by mean `overall` score, among methods or beans with at least `StatisticsRules.minimumRatedBrews` rated brews. On an equal mean, more rated brews win, then the most recent brew; a full tie falls back to the vocabulary order (methods) or the bean's local id, so the result never depends on the store's order.
  - Buy again: the share of yes among the ratings that answer it; an unanswered rating is not a no (ADR 0026).
- **How shown.** Means with `StatisticsRules.meanFractionDigits` (one) decimal and the share as a whole percentage, in the device locale (`StatisticsRules.meanStyle()`, `shareStyle()`). With no brews or no rated brews a section shows an empty state, never zeros. Rated brews that score only criteria this build does not know get their own text in the taste profile. Criterion, method and note labels come from contracts/i18n through `Text(verbatim:)`; the bean is shown with `BeanSummaryView`, so unconfirmed Open Food Facts text is not shown and confirmed text only through `Text(verbatim:)`. Plain lists, no charts.
- The thresholds are defined only in `StatisticsRules`; `scripts/ios-scripts.test.mjs` checks that, and that the statistics sources write nothing and have no typed text.
- Tests: `PersonalStatisticsTests` (the ADR's thresholds, one decimal in de and en, the empty state, unrated brews, means and partly scored ratings, the per-method threshold, top notes with ties and unknown ids, best method and bean with threshold and both tie rules in either input order, the buy-again share without unanswered ratings, removed brews, ISO weeks across New Year and across the end of summer time in Europe/Berlin, ratings that score only unknown criteria) and `StatisticsModelTests` (read from an in-memory store without removed brews, with the shelf entry's bean, and no outbox change; scheduled reloads coalesced into one, and dropped by an immediate one).

## Onboarding and Settings

`Onboarding/` and `Settings/` (M2-T29) implement docs/07 D1 (ADR 0017: opt-in) and the docs/03 risk "Plain consent at onboarding; an opt-out that keeps the personal log working". There is no local-only mode to offer (ADR 0020): onboarding follows Sign in with Apple.

- **When.** `ShelfRoot` puts `OnboardingGate` before the shelf of each account's store. `OnboardingRules.decision` decides from the local profile and `SyncHost.serverProfile` (the last completed pull's `PullReport.profileFound`, else `unreachable` after a failed pull, else `notYet`):
  - a local profile, also one still waiting to be sent, means the shelf, for good: onboarding is never shown again;
  - without one, `GET /profile` 404 shows onboarding, a found profile (stored by the pull, or one this build cannot read) never does;
  - offline, a failed pull shows it at once; with no answer yet (for example a sync stuck behind a retry), the gate shows a progress view for `OnboardingRules.serverWait` (5 s) and then onboarding, so nobody is blocked;
  - a profile that a later pull stores (the server had one after all) ends onboarding while it is open, and finishing then writes nothing.
- **A server profile is merged, never overwritten.** A profile made on this device that the server never confirmed (`pendingCreate`) is checked with `GET /profile` before its `PUT` (`SyncEngine.putProfile`, ADR 0025 Addendum M2-T29). A 404 sends ours. On a 200 the local profile is read again after the answer, so an edit made meanwhile counts, and merged (`SyncEngine.resolvedProfile`): the server's locale, and consent only if both the server and this device say yes, so the user's own "no" here is never undone without them. If the merge equals the server's profile it is adopted and nothing is sent; otherwise it is stored, the profile becomes `pendingUpdate`, and the same operation sends it as `PUT /profile`. The check counts as an attempt (not when cancelled) and backs off like a send.
- **Pages.** `OnboardingPage`: two intro pages (the log; private and offline), then the consent: what is shared (ratings, while sharing is on, with method and recipe values, without name or account, into community figures that subscribers and people who rated the same coffee see, shown only from 5 raters), what is not (shelf, recipes, statistics, anything about the user), and that declining changes nothing in the personal log. The agree control is a `Toggle`, off by default. "Next" moves on and, on the consent page, finishes with the control's value; "Skip", on every page, finishes with false whatever the control says. First run: 3 taps with Next (4 with agreeing), 1 with Skip.
- **Write.** Finishing calls `AccountStore.setProfile` (inside its `write { }`), which queues `update profile` in the same save, so it works offline and the outbox sends `PUT /profile` later. The body carries `locale` (`OnboardingRules.profileLocale`: `VocabularyLanguage.resolving`: the first of `Locale.preferredLanguages` whose language code is German or English, `de-CH` and `de-AT` included, other languages skipped, else `en`; exactly `de` or `en`) and `consent.contribute_to_aggregates`. A failed save says so and stores nothing.
- **Settings.** The shelf has "Settings" (`SettingsRoute`, one tap) under "Statistics". `SettingsScreen` is a list of sections, one function each: Privacy, Export (M2-T30), the data of other accounts (M2-T30) and Delete Account (M2-T31). The consent `Toggle` shows the stored value (false without a profile) and writes it with `setProfile`, which queues `PUT /profile`; the stored locale is kept. Consent gates nothing on the device: with it off the shelf, brews, ratings, recipes and statistics work the same. A failed save shows the stored value again with a note.
- Tests: `OnboardingTests` (a 404 after sign-in leads to onboarding through `SyncHost` and a 200 skips it, a failed pull shows it, the wait, no onboarding once a local profile exists, the false default and Skip on every page, agreeing, a failed save, the locale mapping and the locale sent, an offline completion queued and sent once online, the merge with a server profile (server yes and local no sends no, also after a Settings change or an edit during the read; server no stays no; both yes adopts), a failing read backing off one attempt per cycle, an unreadable profile parked, finishing after a pulled profile writing nothing, the toggle sending `PUT /profile` on and off, turning consent off with shelf, brew and recipe writes still sent, a failed toggle save). `scripts/ios-scripts.test.mjs` checks no typed text, the false default and Skip, writes through `setProfile` only, the gate before the shelf, Settings one tap from it, and the engine's check.

## Sign-in

`Auth/` (M2-T11, ADR 0024) signs in through the Cognito hosted UI with Sign in with Apple as the only provider. It needs no package, no Sign in with Apple entitlement and no registered URL scheme.

- `SignInView` has one control, `AppleSignInButton`: drawn to Apple's guidelines, not `AuthenticationServices.SignInWithAppleButton`, which always starts the native request (it needs the entitlement and returns a token the hosted UI cannot take). The app asks for no name and no email.
- The button opens `ASWebAuthenticationSession` (`SystemWebAuthenticator`, ephemeral, callback scheme `cupmark`) on `/oauth2/authorize` with `response_type=code`, `client_id`, `redirect_uri=cupmark://auth`, `identity_provider=SignInWithApple`, `scope=openid`, a random `state` and an S256 `code_challenge` (`PKCE`: 32 `SecRandomCopyBytes` bytes, CryptoKit SHA-256, base64url). `AuthorizationRequest.code(fromCallback:redirectURL:)` rejects another URL, a missing, repeated or different `state`, an OAuth `error` and a missing code. Closing the sheet is `AuthError.cancelled`, which shows no error.
- `CognitoTokenEndpoint` posts `application/x-www-form-urlencoded` to `/oauth2/token` (code with `code_verifier`; refresh token) and `/oauth2/revoke`, with `client_id` and no client secret. Only an error body's `error` code is read (`invalid_grant`). A network failure is `APIError.transport`.
- `AuthSession` is an actor and the app's `TokenProvider`. The refresh token and the `AccountID` are one Keychain item (`KeychainCredentialStore`: generic password, service `app.cupmark.Cupmark.auth.<stage>`, account `refresh-token`, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`). The access token is kept in memory only; the id token is read for its `sub` and dropped. A token is refreshed 120 s before it expires (or at half its lifetime, if shorter) and on a 401 (`refresh()`); concurrent callers share one refresh task, and a caller that asks during a refresh waits for it. `invalid_grant` ends the session (`AuthStatus.sessionExpired`); a transport failure, a Cognito 5xx, a 429 or an unusable response keeps it, so the app works offline; `APIClient` reports these as `transport`, `serviceUnavailable` or `tooManyRequests`, and only sign-in-again failures (`sessionExpired`, `notSignedIn`, `accountMismatch`) as `unauthorized`.
- Sign-out clears memory and the Keychain, then revokes the refresh token; a failed revoke still leaves the device signed out.
- `AuthModel` (`@Observable`, main actor) holds the phase (`restoring`, `signedOut`, `signingIn`, `signedIn(AccountID)`) and the note to show (`Failure`: sign-in failed, offline, session expired; since M2-T31 also `signInRequired`, "this account was deleted, or its sign-in ended", and `accountDeleted`, which is not shown as a problem). `signOut(reason:)` signs out with a note; `signInAgain()` runs the web sign-in while signed in and replaces the saved sign-in only when it succeeded (account deletion, which never signs out before its 204). `CupmarkApp` builds it with `AuthModel.live(config:)` when the stage is configured and puts it in the environment; `AuthGate` in `RootView` shows the sign-in screen or the signed-in content and, for now, a sign-out toolbar button.
- **`AccountID` (for M2-T15).** The local store key: the lowercase hex SHA-256 of the id token's `sub`, 64 characters, file-name safe. Read it from `AuthModel.accountID` or from the closure argument of `AuthGate`. It is available offline at launch (saved in the Keychain). It is never sent: the backend takes the user from the access token (invariant 3). The id token's signature is not checked, because the value only picks a local store (ADR 0024).
- Tests: `PKCETests` (RFC 7636 appendix B), `HostedUITests` (authorize URL, callback checks), `TokenEndpointTests` (form bodies, no secret, decoding, errors, with `StubURLProtocol`), `AccountIDTests`, `AuthSessionTests` (single-flight refresh, expiry, offline, sign-out), `AuthModelTests` (the flow with a fake web sheet), and `KeychainCredentialStoreTests`, a real Keychain round trip in the test host app that is skipped if the simulator gives the unsigned build no Keychain. Fakes are in `CupmarkTests/Support/AuthFakes.swift`.
- Only a device run against dev (M2-T34) shows the Apple sheet, the callback and a real token exchange.

## Strings

- Every UI string is a key in `L10n.swift` with English and German in `Localizable.xcstrings`. Vocabulary labels come from `contracts/i18n` and are shown with `Text(verbatim:)`.
- Every catalog entry has `"extractionState" : "manual"`: the catalog is maintained by hand together with `L10n.swift`, and `manual` tells Xcode not to mark an entry stale when its extraction does not find the key in code. Add it to every new entry.
- `node scripts/check-ios-strings.mjs` checks the catalog on Linux: both languages present and translated, `extractionState` manual, no unused or missing key. It also fails on shown text that bypasses `L10n` in any Swift file under `ios/` (comments ignored):
  - a string literal as the first argument of `Text`, `Label`, `Button`, `navigationTitle`, an accessibility modifier or the other calls in `UI_CALLS`, also when the literal is on a later line than the call;
  - any string literal inside `Text(verbatim: ...)`, including a fallback such as `?? "n/a"`;
  - a name bound to a string literal in the same file (`let title = "Hi"`) passed as the first argument of one of those calls.
  Literals that are not shown text, such as `Image(systemName:)` or `systemImage:`, are allowed.
- `InfoPlist.xcstrings` localises the Info.plist permission strings. `check-ios-strings.mjs` checks it with the same rules and requires exactly the `INFOPLIST_KEY_NS...UsageDescription` settings of `project.pbxproj`, with the English value equal to the build setting.
- **Localisation pass (M2-T32).**
  - Language: one rule, `VocabularyLanguage.resolving(preferredLanguages:)` (the first preferred language that is German or English, in any region; other languages such as `fr` are skipped; none matching gives English; it is what the UI text shows, so labels and UI text never mix languages), used by the profile locale (`OnboardingRules.profileLocale`) and by `VocabularyLanguage.current`, the language of every vocabulary label. A label or question missing or empty in that language falls back to English (`VocabularyStore`); an unknown id still throws.
  - Numbers, units and durations use Foundation (`BrewFormat`, `BrewTimerFormat`, `RatingFormat`) with the device locale; dates use `DisplayDate.day` and `DisplayDate.dayAndTime` (`Date.FormatStyle`). The timer reads `m:ss` and `h:mm:ss` from one hour (`48:00:00` at the largest `brew_time_s`, never days). The ratio's `1:` is the catalogue key `brew.ratio.value %@`. Data sent to the server (RFC 3339, `YYYY-MM-DD`, JSON numbers) and the export file name are never localised. Tests pin the formatter locale (`FormattingTests`).
  - `check-ios-strings.mjs` also fails a catalog value whose number of `%@` placeholders differs from its key's.
- `scripts/check-no-free-text.sh` fails on any control that accepts typed text.

## Accessibility

M2-T33, docs/04 Non-functional (Dynamic Type and VoiceOver on every control).

- **VoiceOver label and value.** Every slider, stepper and pick list has a label (the criterion or field) and a value. A value with a unit is read as shown ("Dose, 18.0 g"); one on a scale without a unit is read on its scale: a score "Aroma, 7.5 of 10" (`RatingFormat.spokenScore`), the normalised grind and the grind setting "4.5 of 10" (`BrewFormModel.spokenValueText(of:)`, `spokenGrindSettingText()`), through the format key `accessibility.value_of_scale %@ %@` (`AccessibilityValue.ofScale`). The long pick lists (`IndexedPickListRow`) read "Origin, Not set" like a `Picker`; a segmented picker with a hidden label has an accessibility label. Scores and steppers are the native `Slider` and `Stepper`, so VoiceOver adjusts them with swipes up and down.
- **Tap targets.** Borderless buttons (Clear, the stepper's clear icon, the label photo row) are at least 44 by 44 points (`minimumTapTarget()`); bordered buttons in bars, fallbacks and the timer use the large control size. The A to Z index letters stay small, like the system section index, and are hidden from VoiceOver.
- **Largest text sizes.** `ContentUnavailableView` does not scroll, so the scanner fallback, the lookup fallback, the pending bean and "not configured" are wrapped in `FitsOrScrolls` (as is at the default size, scrolling when too tall). The Sign in with Apple title has no line limit.
- **Images.** Decorative symbols are hidden from VoiceOver; a symbol that is a button's whole label has the button's label.
- **UI tests.** `CupmarkUITests/AccessibilityAuditTests` launches each screen with `-CupmarkUITestScreen <screen>` and runs `performAccessibilityAudit()` at the default size and at `UICTContentSizeCategoryAccessibilityXXXL`, English pinned: sign-in, not configured, onboarding, shelf, scanner fallback, lookup result, pick-list entry, brew form, the running timer, rating, recipes, statistics and settings. The audit reports its findings as `AUDIT-ISSUE` lines in the log and does not fail the build (owner decision, 2026-11-26); the tests that fail are the screen not appearing and the VoiceOver value tests. Filters, each commented in the test: the audit's own uncertain verdicts ("Contrast nearly passed", "Dynamic Type partially unsupported") are not reported; the Dynamic Type check is left out at the pinned largest size and the clipping check at the default size; and three narrow exclusions: contrast on a disabled control (WCAG exempts inactive controls), hit region of UIKit's own segmented control and stepper, and clipped text inside the navigation bar. Further tests read a score's label and "x of 10" value and move it, increment the dose stepper and read "x g", and read a pick list's label and value.
- **The UI-test start** (`UITestSupport/`, Debug only). `CupmarkApp` reads `-CupmarkUITestScreen` only inside `#if DEBUG`; with it, the window shows `UITestRootView` and nothing of the app's own start runs (no Keychain, no export folder, no network). Sign-in, onboarding and the shelf go through `RootView`, `AuthGate` and `SyncHost` on a real `AuthModel` with an in-memory credential store and fake Cognito endpoints; the other screens are shown on their own in a navigation stack. The store is `AccountStore.inMemory()` with `UITestFixtures` (two bags, rated brews of three methods, an unrated brew, recipes, a profile), all synced, so the outbox is empty; the engine's account check says no anyway. `UITestAPI` answers the fixture barcode with a catalogue bean and every other request with 503, on `api.cupmark.test`, through a `URLProtocol` of its own session. Without the argument a Debug build starts exactly as before; a Release build has neither the argument nor the code.
- **Checks on Linux.** `node scripts/check-ios-accessibility.mjs` fails a slider or stepper without an accessibility label and value, a hidden picker label without an accessibility label, a symbol that is neither hidden nor labelled, a borderless button without `minimumTapTarget()` (unless the line before says `// Tap target: ...`), a `UITestSupport/` file that is not one `#if DEBUG` block, and any mention of the UI-test start outside `#if DEBUG` in the app or the unit tests. `UITestSupportTests` and `AccessibilityValueTests` test the parts that run without the simulator UI.

## Look

M2-T41, ADR 0032. A warm espresso and cream look on system fonts; the sets are the only place a colour value is written.

- **Palette** (`Assets.xcassets`, each with a light and a dark `appearances` value, sRGB): `AccentColor` (espresso `#6B4428`, caramel `#E0B27E` in dark), `OnAccent`, `FormBackground`, `ListBackground`, `Surface`, `TextPrimary`, `TextSecondary`, `SwipeAction` and `SwipeActionSecondary` (backgrounds of swipe actions, whose labels the system draws in white) and `ErrorText` (error text and its icon; the system red is 3.0 to 3.4:1 on cream, so `.red` stays only for the destructive button role). The values and their contrast table are in ADR 0032. `AccentColor` is also the global tint (`ASSETCATALOG_COMPILER_GLOBAL_ACCENT_COLOR_NAME`), so buttons, links, sliders, steppers and pickers take it without a modifier; a `Toggle` stays green unless it has `.tint(Theme.accent)`, so every toggle has it.
- **One file reads them:** `Theme/Theme.swift` (`Color("Name")` by name, so it works with or without generated symbols). `Theme.accent`, `.onAccent`, `.formBackground`, `.listBackground`, `.surface`, `.textPrimary`, `.textSecondary`, `Theme.titleFont(_:)`, and the modifiers `formBackground()` / `listBackground()` (hide the system's scroll background and show the named one), `screenBackground()` (plain screens and fallbacks), `surfaceRow()` (on a `Section` or a row), `secondaryText()`, `accentText()` (scores, selection marks), `themeTitle(_:)` (system font, `.rounded` design, bold, Dynamic Type unchanged) and `.buttonStyle(.prominent)` (accent fill with `OnAccent` text; the system's `.borderedProminent` writes white, which fails on caramel).
- **Rules:** a `Form` or `List` gets `formBackground()` or `listBackground()` and its sections `surfaceRow()`. Captions, footers, headers and hints use `secondaryText()`, never `.secondary` (a translucent grey that nearly fails 4.5:1 on cream). Scores, the rating sliders and the selected mark of a pick list use the accent. `.red` is for errors and destructive actions only. `.primary` stays for body text. `.white` and `.black` are only in the Sign in with Apple button, whose colours Apple fixes. Navigation bar titles stay the system's.
- **Check:** `node scripts/check-ios-colours.mjs` fails on `Color(red:`, `Color(white:`, `Color(hue:`, `UIColor(`, a hex string, `Color("Name")` outside `Theme/`, a system colour as a brand tint (`.indigo`, `.blue`, `.orange`, ...), the system's secondary colours as text colour, and on a colour set pairing below 4.5:1 in either appearance. Tests: `scripts/ios-colours.test.mjs` (Linux CI) and `CupmarkTests/ThemeColourTests` (Mac), both recompute every pairing of ADR 0032 from the colour set JSON.
- **Adding or changing a colour:** edit the set's `Contents.json` (or add `<Name>.colorset` with a light and a dark value), read it in `Theme.swift`, add it to `COLOUR_NAMES` and its pairings to `PAIRINGS` in `scripts/check-ios-colours.mjs` and `ThemeColourTests.pairings`, and update the table of ADR 0032 (a decision change needs a new ADR). A value that fails 4.5:1 fails both tests.

## Project file

`Cupmark.xcodeproj` is written by hand, using Xcode 16 synchronized folders (`PBXFileSystemSynchronizedRootGroup`, object version 77): every file under `Cupmark/`, `CupmarkTests/` and `CupmarkUITests/` belongs to its target without a per-file entry. Adding a Swift file needs no project change, so it can be done without a Mac. XcodeGen was not used because CI would have to download an unpinned or separately verified binary.

Targets: `Cupmark` (the app), `CupmarkTests` (unit tests, hosted in the app, `TEST_HOST`) and `CupmarkUITests` (UI tests, M2-T33: `com.apple.product-type.bundle.ui-testing`, `TEST_TARGET_NAME = Cupmark`, no host). Both test targets are in the `Cupmark` scheme's test action. `node scripts/check-xcode-project.mjs` checks the project file and the scheme on Linux: every object id defined once and every referenced id defined, each target with its configuration list (Debug and Release), build phases, product and dependency proxy, a UI-test target without `TEST_HOST`, and every test target in the scheme's test action.

Signing: bundle id `app.cupmark.Cupmark`, automatic signing, no team id. Simulator and CI builds pass `CODE_SIGNING_ALLOWED=NO`. A device build needs the developer's own team, set locally and not committed.

## Build and test

```
cd ios
xcodebuild test -project Cupmark.xcodeproj -scheme Cupmark \
  -destination 'platform=iOS Simulator,name=iPhone 16,OS=latest' \
  CODE_SIGNING_ALLOWED=NO
```

This runs both test targets, the unit tests and the UI tests (M2-T33); add `-only-testing:CupmarkTests` for the unit tests alone. The UI tests need a simulator with iOS 17 or later (`performAccessibilityAudit()`).

CI runs the same on `macos-15` with Xcode 16.4 (job `ios` in `.github/workflows/ci.yml`). On a pull request the job runs only when the `changes` job finds a changed path under `ios/`, `contracts/vocabulary/`, `contracts/i18n/`, or a change to `contracts/openapi.yaml`, `contracts/lib/vocabulary.mjs`, `contracts/lib/lock.mjs`, `contracts/lib/openapi.mjs`, `scripts/generate-ios-vocabulary.mjs`, `scripts/generate-ios-api.mjs`, `scripts/check-ios-strings.mjs`, `scripts/check-ios-accessibility.mjs` or `ci.yml`: the app and every input the iOS generators read. `scripts/check-workflows.test.mjs` derives those inputs from the generator scripts and fails if `IOS_PATHS` in `ci.yml` lacks one. Pushes to `main` always run it, and so does any run where the diff cannot be computed. `ci-ok` accepts a skipped `ios` only when `changes` said `ios=false`.
