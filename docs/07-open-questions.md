# Open questions and human tasks

## Open decisions

Since ADR 0014, the lead decides these on its own recommendation and records each answer here and in an ADR ("decided by: lead (ADR 0014)"). It asks the owner first only when a decision is likely to add cloud costs. Until a question is answered, agents build to the stated default and mark the code path with the decision id.

| Id | Question | Default the agents build to |
| --- | --- | --- |
| D1 | Opt-out or opt-in for contributing to aggregates? Opt-in is safer under GDPR but shrinks the data set. | **Answered 2026-11-25, decided by: lead (ADR 0014, ADR 0017):** opt-in, asked once at onboarding. The profile stores `consent.contribute_to_aggregates`; the app sends false unless the user agrees. The aggregator (M3) counts only brews whose author had consent at write time. |
| D2 | What happens to a deleted user's contribution to aggregates? | **Answered 2026-11-25, decided by: lead (ADR 0014, ADR 0017):** subtract it, then delete. Account deletion deletes every brew item, and the aggregator (M3) subtracts each removed brew from the stream's old image, as it does for any brew delete. No aggregates exist before M3, so M1 needs nothing more. |
| D3 | Who curates the catalogue? | The operator, through a CLI script |
| D4 | Price points | 2.99 EUR a month, 19.99 EUR a year |
| D5 | How does Open Food Facts share-alike apply to the bean catalogue? | Tag source per field, keep catalogue separate from ratings; lawyer to confirm |
| D6 | Keep the give-to-get teaser for free users? | Yes |
| D7 | F1 step 3 stores an Open Food Facts hit as a catalogue entry (name, brand), and docs/05 caches results in the catalogue, but the API accepts no free text. May Open Food Facts name and brand be stored and returned once fetched by the server or verified by the operator, or does F1 step 3 need a roaster pick list instead? | **Answered 2026-11-25 (ADR 0005):** store and show what Open Food Facts has; the backend fetches it, and the app has no free-text input. The contract carries them as response-only fields since M1-T8. |
| D8 | docs/04 F1 and the docs/05 data model need roaster, origin and variety lists (with a curated roaster list), but vocabulary v1 has none of them, so F1 cannot describe a bean fully. When does a vocabulary v2 with these lists come, and who curates the roaster list? | **Answered 2026-11-25 (ADR 0006):** origin and variety lists go into vocabulary v2; roaster comes from the Open Food Facts brand and is curated by the operator. They stay out of the API until the owner approves vocabulary v2 (draft in M1-T8). |
| D10 | When a user deletes their account, what happens to their label photos? Photos are versioned, so a plain delete keeps them for 30 days as old versions. | **Answered 2026-11-25 (owner):** delete every version of the photos the user uploaded, immediately. Photos of beans that are already verified stay, because they belong to the shared catalogue, but they are no longer linked to the user. |
| D11 | A deleted user's data stays in point-in-time recovery for up to 35 days and in the weekly exports for about 395 days. Is that acceptable if the privacy policy discloses it, and must a restore re-apply deletions? | **Answered 2026-11-25 (owner):** acceptable if disclosed in the privacy policy. A deletion log of ids only is kept, and every restore re-applies it before the data is used. |
| D12 | Should label photo uploads have their metadata (EXIF, GPS) stripped? | **Answered 2026-11-25 (owner):** strip all metadata (EXIF, XMP, GPS) before a photo is stored for review or shown. |
| D13 | docs/04 F2 says brew fields depend on the method, but no mapping exists. Which fields apply to which method? The grinder pick list and the grind setting on the grinder's own scale are also missing from the contract. | **Answered 2026-11-25, decided by: lead (ADR 0014, ADR 0021):** rules and a grinder list with per-grinder scales live in vocabulary v3 (M2-T2 to M2-T5). `cold` and no temperature for cold brew; no temperature for moka pot and cezve; no grinder or grind setting for fully automatic; the grind setting must lie on the chosen grinder's scale. The owner approves the grinder list when v3 is published (M2-T4). No cloud cost. **Approved by the owner 2026-11-26:** the v3 draft as it stands (grinder list, grinder scales, the three grinders without a scale, `df64` at the step the draft has (1), the `sage_` ids, the method field rules); v3 published in M2-T4. |
| D14 | May `PUT /shelf/{id}` change `bean_id` while brews reference the entry? | **Answered 2026-11-25 (owner):** no. The API answers 409 while `brewCount` > 0. To correct a bean, delete the brews or add a new shelf entry (task M1-T10). |
| D15 | What does the lookup answer for a product whose only content is its front image when the image copy fails? | **Answered 2026-11-25, decided by: lead (ADR 0014):** a transient failure (timeout, network, HTTP 429 or 5xx, S3, no bucket configured) is 503 and caches nothing, so a later lookup tries again. A permanent failure (redirect, other 4xx, wrong content type, too large, not a JPEG) is cached as a miss (404). Both count against the lookup cap. A product with a name or brand stays a hit without an image (M1-T4c; docs/05 Image copy). No cloud cost. |
| D16 | Should the app offer a local-only log without sign-in? | **Answered 2026-11-25, decided by: lead (ADR 0014, ADR 0020):** not in M2. Sign in with Apple is required; it already keeps the user anonymous to others. The local store is keyed by account so an offline account can be added later; revisit after the TestFlight round (M6). No cloud cost. |
| D9 | Should the health route (M0-T3, smoke test in M1-T7) be reachable without a token? | **Answered 2026-11-25 (ADR 0007):** `GET /health` needs no token and returns only `{"status":"ok"}`. It is added to the contract in M1-T8 as the single documented lint exception. |

Record each answer as an ADR in `docs/decisions/`.
