# 0033 Brew photos stay on the device: local schema version 4, one folder per account, and their deletion

- Status: accepted
- Date: 2026-11-26
- Decided by: lead (ADR 0014), on the owner's decision of 2026-11-26 that brew photos stay on the device; no cloud cost

## Context

The owner decided that a brew can have photos, kept on the device only: nothing is uploaded, nothing goes to the CSV export, there is no cloud cost and no change to the App Privacy answers. M2-T42 builds the local model, the files and every way they are deleted; the capture (M2-T42b), the gallery (M2-T43) and the viewer (M2-T43b) build on it. A photo has no caption or any other text (invariant 1). There is no endpoint, no contract change and no outbox operation.

The task leaves open how the photo is stored and linked to its brew, how a local schema version is added for it, where the files live, whether device backups include them, how metadata is removed, and how the files follow every way a brew, an account or another account's data leaves the device.

## Decision

- **Local schema version 4 with one new model.** `CupmarkSchemaV4` lists version 3's models unchanged and adds `StoredBrewPhoto`: `localID` (unique), `brewLocalID`, `fileName`, `createdAt`. It has no `serverID`, no sync state and no `vocabularyVersion`, since it is never synced and holds no vocabulary value. `CupmarkMigrationPlan` gets a lightweight stage from 3 to 4 (it only adds an entity), the way ADR 0030 added version 3: a new version rather than an edit of version 3, since stores of version 3 may exist on development devices. Only the new type alias `StoredBrewPhoto` is added; the other aliases stay on the versions whose models they are, because version 4 changes none of them. `AccountStore.schema` is version 4. `StoredBrewPhoto` is in no API type, no outbox operation and not in the export (the export is the server's `GET /export`).
- **Linked by the brew's `localID`, no relationship.** A SwiftData relationship would change `StoredBrew` (and, through it, `StoredShelfEntry` and `StoredBean`) and their hashes, so the stage would no longer only add an entity. The link is the brew's `localID`, which never changes. The cost is that SwiftData does not delete the photos with the brew; the store does that on every removal path (below) and the sweep catches what is left.
- **Files, one folder per account.** A photo is a JPEG `Application Support/BrewPhotos/<account id>/<UUID>.jpg` (`BrewPhotoFolders`, `BrewPhotoFileStore`), next to `LabelPhotos`, one folder per account like the store (ADR 0020). The folder name is the `AccountID`, 64 lowercase hex digits checked by `AccountID(rawValue:)`, as for the label photo folders, so no account id names a path outside the root; a store whose account id is not an `AccountID` has no photo folder and cannot add photos. Only names of the form `<UUID>.jpg` (upper-case, as written) are ever turned into a path, so a stored name cannot reach outside the folder.
- **Writing a file.** The bytes go to a hidden temporary file in the same folder (`.<UUID>.partial`), written with `.withoutOverwriting` and `.completeFileProtection`, which is then moved to its name: a file with a photo name is always complete. A photo is at most 2 MiB (below), so the store writes it on its own actor (the main actor in the app) without a hop; the encoding, which is the slow part, runs off the main actor (`BrewPhotoEncoder.encodeInBackground`). Only `Data` and the `Sendable` encoded photo cross that hop, never a model.
- **The limit is 6 per brew** (`BrewPhotoLimits.maxPerBrew`). A seventh is refused with `BrewPhotoError.limitReached` before any file is written. A brew the user removed (`pendingDelete`) or one of another store takes none (`brewNotFound`).
- **Metadata is stripped on the device by `LabelPhotoEncoder`**, with its own `Limits` for local photos, `BrewPhotoLimits.encoding`: 2048 px on the longest side, 2 MiB, qualities 0.85, 0.75, 0.65, 0.55 and 0.45 (the upload limits are 4096 px and 8 MiB). 2048 px is more than a phone screen's width in pixels; 2 MiB keeps a full brew under 12 MiB. The encoder applies the orientation to the pixels, redraws them into a fresh bitmap and keeps only SOI, APP0 (JFIF), APP14 (Adobe) and the image segments, so no EXIF, GPS, TIFF or XMP of the input is stored. `EncodedBrewPhoto` can only be made by `BrewPhotoEncoder`, so the store cannot be handed bytes that were not stripped.
- **Device backups include the files.** Unlike the label photos (which are only a waiting copy of an upload and are excluded), a brew photo is the user's own data with no other copy, so an iCloud or computer backup of the device keeps it, and a restored device has it again. The folder is therefore not marked `isExcludedFromBackup`. The protection class is `.completeFileProtection`, as for the label photos: the files are only read by screens, which run while the device is unlocked, and no background work reads them (nothing is uploaded). A backup includes files of every protection class. The privacy text of the companion page says nothing about device backups, so nothing in it is contrary; M2-T42b adds the sentence that brew photos stay on the device.
- **Store API** (`Store/AccountStore+BrewPhotos.swift`): `addBrewPhoto(to:jpeg:createdAt:)` writes the file, then saves the record in one `write { }`; when the save fails (or anything in the write throws), the file is deleted again. `brewPhotos(of:)` and `allBrewPhotos()` list newest first (then by file name, so the order is stable). `brewPhoto(localID:)`. `brewPhotoFileURL(of:)` reports a missing file (or a name that is not a photo name) as `BrewPhotoError.fileMissing` with a fixed log message, never a crash; the record stays, so the user can delete it. `deleteBrewPhoto(_:)` deletes the record and the file; one that is already gone changes nothing.
- **A deleted record's file goes after the save.** Deleting a record stages its file name (`AccountStore.brewPhotoFilesToRemove`); `save()` deletes the files once the save succeeded, and a failed write forgets them (`discardUnsavedChanges()`), since its records come back (ADR 0025, Addendum M2-T35). A file is only deleted when no record lists its name any more. An app ended between the save and the file deletion leaves a file without a record, which the sweep deletes.
- **Every path that removes a brew deletes its photos**, through `AccountStore.deleteFromDevice(_:)` (the user's delete through `removeBrewPhotos(ofBrewLocalID:)`, since it may keep the brew):
  - the user's delete (`markDeleted`): at once, also when the brew is kept as `pendingDelete` until the server answers, since the photos are on the device only and nothing waits for the server;
  - the sync engine's removals (`removeLocally`: a 2xx or 404 on the delete, a create that never reached the server, a 404 on a `PUT` whose read is a 404 too);
  - a pull that drops a brew deleted on another device;
  - discarding a sync issue that removes the brew (a parked create, or any operation of a brew without a server id).
- **The sweep at store open** (`sweepBrewPhotos()`, called by `SyncHost` right after it opens the account's store, next to the label photo queue's cleanup): first the records whose brew is gone or `pendingDelete`, with their files, then every entry of the account's folder that no record lists (files whose record never reached the store, temporary files of a write that was cut short). If the records cannot be read, no file is deleted. A file whose record exists but whose file is missing is left to the user.
- **Accounts.** A sign-out keeps the photos with the account's store, as it keeps the store (ADR 0020), and another account's sign-in does not touch them. Account deletion (ADR 0031, point 6) also deletes `BrewPhotos/<account>/` of each listed account after the 204, with the label photo folder and before the sign-out (`AccountLocalData.remove`), and is safe to repeat. "Remove Data of Other Accounts" (M2-T30, `LocalDataRemover`) deletes the other accounts' brew photo folders with their stores. While a deletion is recorded no store is opened, so no sweep runs and nothing is deleted before the 204.
- **Privacy manifest.** The new code uses `FileManager` to create a folder, list it (`contentsOfDirectory` without resource keys), check that a file exists, move and remove files, and `Data.write`. None of these is a required-reason API: no file timestamp is read (the order comes from `createdAt` in the store), and no disk space, user defaults, system boot time or active keyboard API is used. The manifest keeps its one entry (file timestamps, C617.1, for the label photos' stale-file cleanup) and gains none. The App Privacy answers do not change, since nothing is collected.

## Alternatives

- **A relationship from `StoredBrew` to its photos with a cascade delete:** SwiftData would delete the records with the brew, but not the files, so the paths would need the same work for the files; and `StoredBrew`, `StoredShelfEntry` and `StoredBean` would need new copies in version 4 and a stage that changes three entities.
- **Photos as `Data` in the store (`.externalStorage`):** SwiftData would manage the files, but the store would hold up to 12 MiB per brew in its context and in every failed-write restore (ADR 0025 Addendum M2-T35 reads saved copies), and the account cleanup and the sweep would depend on SwiftData's private file layout.
- **Exclude the files from backups, as for the label photos:** a lost or replaced phone would lose every brew photo, which exist nowhere else.
- **Deleting the photos of a user-deleted brew only when the server confirms the delete:** the photos would stay on the device, hidden, until the next sync, possibly for days. The one case where a removed brew comes back (discarding a parked delete, ADR 0025 Addendum M2-T18) then has no photos; that is rare and matches what the user asked for.
- **Writing the file in a detached task:** a file of at most 2 MiB written atomically takes milliseconds; a hop would need the store's actor to wait for the write and then insert the record, with the sweep possibly running in between.

## Consequences

- No cloud cost, no endpoint, no contract or vocabulary change, no outbox operation.
- A brew holds up to 12 MiB of photos on the device and in the device's backup.
- A removed brew whose deletion the user later discards (a parked delete) comes back without its photos.
- A record whose file is missing (for example after a restore of a backup made in between) counts towards the limit of 6 until the user deletes it.
- After an account deletion the photos may still be in the user's own earlier device backups, which the app cannot reach.
- Migration tested only in the simulator: the version 3 to 4 migration is tested with a real version 3 store file in `StoreMigrationTests` on the macOS runner, not on a device store.

## Addendum M2-T42b: capture and pick

- The photo library is reached only through SwiftUI `PhotosPicker` (iOS 16 and later; the app's minimum is 17), which runs out of process and hands the app only the photo the user picked. So there is no `NSPhotoLibraryUsageDescription`, no photo library authorisation and no `photoLibrary:` argument (which would make the picker return asset identifiers and ask for access). The camera uses the existing `NSCameraUsageDescription`, whose text (en and de) now also says the camera photographs a brew.
- The privacy manifest needs no change, checked against the required-reason API categories: the picker and the camera add none; thumbnails are read with ImageIO from a file URL (no file timestamp, disk space, user defaults, boot time or keyboard API). The App Privacy answers stay as they are, since a brew photo is never sent.
- A photo is added only to a saved brew: the "Photos" section is on the rating screen of a saved brew (the brew sheet's rating after saving, and the brew list's detail), so no draft photo record or temporary photo data exists.
