# 0031 Account deletion on the device: a Keychain record, no sign-out before the 204, and another account only after a tap

- Status: accepted
- Date: 2026-11-26
- Decided by: lead (ADR 0014); no cloud cost (the app only calls the existing `DELETE /account` and Cognito's token endpoint)

## Context

M2-T31 builds account deletion in the app (docs/04, Non-functional) on top of `DELETE /account` (ADR 0017 and its Addendum, contracts `deleteAccount`). The server deletes in the request, answers 204 only when every step succeeded, and is safe to repeat; a repeated `DELETE /account` with a token issued before the deletion answers 204. Its last step deletes the Cognito user, after which no new token can be issued for that user. ADR 0017 requires that the app never signs out or discards tokens before the 204.

The task leaves open what happens when the token cannot be refreshed before a 204, and where the "deletion in progress" state lives so that it survives the store being deleted and the app restarting.

## Decision

1. **A refresh that fails, and another account.** If the token cannot be refreshed before a 204 (Cognito answers `invalid_grant`, or anything else that means "sign in again"), the user is asked to sign in again, and the deletion is retried with the new token. What happens next depends on the account that sign-in gives:
   - **The same account** (its `AccountID` equals the record's): the deletion goes on at once with the new token.
   - **Another account: never deleted without an explicit tap.** A different `AccountID` comes from two cases the app cannot tell apart: Cognito already deleted the user (a 204 was lost), so the same Apple ID created a new, empty Cognito user with a new `sub`; or the user signed in with a different Apple ID, whose account may hold real data. So the deletion stops before any request (`confirmDifferentAccount`) and the screen says, with buttons only: "You signed in with a different account than the one you asked to delete. The account you asked to delete may already be gone, or it may still exist. If you continue, this account and all its data are deleted, and this cannot be undone." "Delete This Account" moves the record to the signed-in account (the local data of both goes after the 204) and goes on. "Sign Out" signs out of that new session only and keeps the record unchanged, so the sign-in screen still asks to finish the deletion; this is no sign-out before the 204 in the sense of ADR 0017, since the session signed out is not the account being deleted and nothing is deleted.
   - The prompt is not stored: it is derived from the saved sign-in and the record, so a restart while it is shown shows it again and never deletes on its own.
   - The sign-in screen and the progress screen say before the sign-in: "Sign in with the account you asked to delete to finish deleting it. If you sign in with a different account, Cupmark asks you before it deletes anything."
   - When the record was moved, the final note says that the account the user signed in with and chose to delete was deleted (`otherAccountDeleted`), never that the account the deletion was started for was.
   - There is no cancel once the deletion started: after a 500 the server may already have deleted part of the account, and a half-deleted account that syncs again would be worse than finishing. "Sign Out" on the prompt leaves the deletion waiting, not cancelled.
2. **Never sign out or delete anything before the 204.** Nothing in the deletion signs out the account being deleted, discards its token or deletes local data before the 204; the hold of the sync host deletes no label photo either. A 500, 429, 503, any other failure and a network failure (also of the refresh) are retried with `SyncBackoff` (2 s doubling to 300 s, equal jitter) until a 204. When the session ended itself (`invalid_grant`), `AuthSession` has already dropped a token Cognito refuses; that is the session's existing rule (ADR 0024), not the deletion's. When the session is still saved but cannot be refreshed, the progress screen's "Sign In Again" runs the web sign-in while signed in (`AuthModel.signInAgain()`) and replaces the saved sign-in only once the new one succeeded; a failure is shown on the screen.
3. **Refresh once per run, then delete.** Every run (the start, every resume: after a restart, a new sign-in, a return to the foreground, a "Try Now") refreshes the token before its first `DELETE /account`, so a partly finished deletion has the token's whole lifetime for its retries. Later attempts within the run use the token as it is; the API client still refreshes it shortly before it expires and on a 401, so a retry within the run after a deletion that finished on the server still gets its 204 with the old token. A resume while a run is under way makes one more run follow it, so a sign-in that finished during a run is never left without one.
4. **The record lives in the Keychain.** `AccountDeletionRecord` (`requested` or `serverDeleted`, the account the `DELETE` is sent for, and every account whose local data goes, the first being the one the deletion was started for) is one generic-password item, service `app.cupmark.Cupmark.deletion.<stage>`, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`. It is written before anything is stopped or sent, becomes `serverDeleted` after the 204, and is removed last, after the local data and the sign-in are gone. The Keychain is outside the store and Application Support, so deleting them never deletes it, and like the saved sign-in it survives a reinstall: a reinstalled app that is still signed in to an account under deletion resumes the deletion instead of syncing it. If the record cannot be saved, the deletion does not start and nothing is sent. A record that is there but cannot be decoded is never deleted for that, since that would release sync to an account whose deletion may be half done: it holds sync like any record, and the app asks (`confirmUnreadableRecord`, "Delete This Account" or "Sign Out") before it deletes the signed-in account and writes a new record over it.
5. **Nothing more is sent.** While a record exists (or cannot be read or decoded), `SyncHost` opens no store and runs no engine for any account, and `AuthSession.maySend(as:)`, which the engine, the pull, the label photo queue and the screen uploads ask before each request, is false. A token refresh, a return to the foreground or a restart cannot start them again.
6. **After the 204**, in this order: the store files of each listed account (`<stem>.store`, `-wal`, `-shm`, so the outbox goes with the data), its label photo folder `LabelPhotos/<account>/` with the `Queued` photos (from the M2-T24 and M2-T25 reviews), the cached catalogue images and export files, then the sign-out (the Keychain sign-in, with the note of point 1), then the record. Each of these steps is safe to repeat. If the app ends after the record became `serverDeleted`, the next start finishes the cleanup without another request. That holds only if saving `serverDeleted` succeeded: if it failed, the record still says `requested`, so the next start refreshes first; for a user Cognito has deleted that refresh fails, the user is asked to sign in again, and the new sign-in is a different account, which is only deleted after the tap of point 1.
7. **The tombstone 401 gets a reason** (from the M2-T16 review). When sync asks for sign-in, the app signs out with the note "This account was deleted, or its sign-in ended". After the refresh the two cases answer the same, so the note names both, and nothing local is removed automatically (M2-T30's decision stands).

## Alternatives

- **Sign out and give up when the refresh fails:** would leave a half-deleted account, or a Cognito user that still exists, with no way to finish from the app.
- **Delete whatever account the new sign-in gives:** the first version of this ADR did that, on the assumption that another account means Cognito had deleted the user. It does not: another Apple ID gives another account too, so an expired refresh token for one account could lead to deleting another with real data and then reporting success. Rejected in review.
- **Never delete another account, only the original:** after a lost 204 the new sign-in is a new, empty Cognito user, and the user could not remove it from the app. The explicit tap covers that case without risking the other.
- **Refresh before every attempt:** after the server deleted the Cognito user, every refresh fails, so a retry that the old token would have finished would instead ask for a sign-in.
- **The record as a file in Application Support:** lost on a reinstall while the Keychain sign-in survives, so the reinstalled app would sync to a half-deleted account. A file inside the store would be deleted with it.
- **Dropping a record that cannot be decoded** (as an unreadable sign-in is dropped): would release sync to a possibly half-deleted account.
- **A cancel button during the deletion:** see point 1.

## Consequences

- Another account is deleted only after "Delete This Account"; the prompt says plainly that it may be a different account with its own data.
- A deletion shows its progress instead of the shelf until the 204; offline it waits and retries, also across restarts.
- A lost `serverDeleted` save after the 204 costs the user a sign-in and a tap (point 6), never a silent deletion.
- Follow-up: a `DELETE /account` that keeps answering 400, 403 or 404 is retried forever; a note after many attempts is left for a later task.
- Cost: none beyond the `DELETE /account` requests ADR 0017 already counts and a Cognito token request per run.
- Revisit if the server's deletion becomes asynchronous (ADR 0017, Alternatives), since the 204 would then no longer mean "deleted".
